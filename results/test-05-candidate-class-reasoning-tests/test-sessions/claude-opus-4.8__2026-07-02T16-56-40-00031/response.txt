**All three candidates fail, and they all fail on the same rule: `R_rec_succ`.**

### Root cause

The rule `recDelta b s (delta n) → app s (recDelta b s n)` **duplicates** the subterm `s`. On the RHS, `s` appears once inside `app` and once inside the recursive `recDelta`. Any measure that is a fixed positive linear combination of subterm measures (with a positive coefficient on `s` in both `app` and `recDelta`) will incur `+μs` from this duplication.

The only decrease this rule provides on the left is peeling one `delta` off `n` (a bounded constant), so the net change is roughly `constant − μs`. When `μs` is large enough, the measure increases. All three measures assign a strictly positive weight to `s` in both constructors, so none can dominate the duplication.

### What would be needed

To handle `R_rec_succ`, a purely additive linear measure over subterms is insufficient because of the duplicated `s`. One would need either:
- A **multiplicative/polynomial** interpretation (e.g., something where the `n`-structure multiplies the cost so that shrinking `n` reduces the number of `s` copies), or
- A **lexicographic** measure with the structural size of the third argument (`n`) as the dominant component (which strictly decreases, ignoring the duplication in the lower component).

None of μ1, μ2, μ3 does this, so **none of the three is a valid termination measure** for this calculus. (Note: the other seven rules are handled fine by all three; the flaw is isolated and identical across candidates.)
