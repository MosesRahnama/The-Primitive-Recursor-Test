## Why LPO specifically

**1. The rules are structurally recursive on a single "counting" argument, not on data content.**

Looking at rule 2:
```
extract_prefix(w,graph,succ(i)) -> extract_prefix_k(w,graph,i,extract_prefix(w,graph,i))
```
the only thing that decreases is the third argument, `succ(i) → i`. Everything else (`w`, `graph`) is copied unchanged, and a *new* function symbol (`extract_prefix_k`) appears wrapping a *recursive call* to `extract_prefix` itself. This is the classic shape that path orders are built for: nested/recursive calls where a subterm of the input reappears as an argument deeper in the output. A polynomial or size-based interpretation would need to argue that `extract_prefix_k(...)` applied to a whole new term (with a recursive call baked inside) is "smaller," which requires knowing something about how `extract_prefix_k` behaves — but we have no semantic information about these symbols beyond the rewrite rules. LPO handles this syntactically via precedence, without needing any interpretation of what `extract_prefix_k` "means."

**2. There's no arithmetic to exploit.**

A polynomial interpretation (assigning weights/degrees to symbols and checking `[lhs] > [rhs]` over ℕ) is the natural first thing to try, but it requires guessing coefficients and verifying inequalities hold for *all* instantiations. Here the structure is purely symbolic — `succ`/`zero` are the only "numeric-looking" symbols, and they're used only as a decreasing counter. There's no multiplication, branching recursion, or size blow-up that would demand real arithmetic reasoning. A precedence-based syntactic order is the more direct and less error-prone fit.

**3. The key decrease is always "strict subterm," which is exactly what LPO is designed to detect.**

In every rule, I could point to a literal subterm relationship:
- Rule 1: `nil` is just a fresh constant, trivially smaller under any precedence with `extract_prefix` on top.
- Rule 2: `i` is a strict subterm of `succ(i)`, which is a strict subterm of the LHS.
- Rule 3: `memo`, `w`, `graph`, `i` are all literal subterms of the LHS reused inside the RHS.

Since every "new" symbol on the RHS (`append`, `cons`, `best_eclass_term`, `nth`) is applied only to arguments that are themselves subterms (or provably-smaller-by-recursion terms) of the LHS, the *subterm property* embedded in LPO's definition does all the work. I didn't need multiset comparisons, lexicographic status was only needed once (rule 2, same head symbol case), and no measure/potential function had to be invented.

**4. It requires only a precedence — the cheapest possible ingredient.**

LPO needs just an ordering on function symbols (which I derived directly from the "calls" structure: `extract_prefix` calls `extract_prefix_k` calls `append`/`cons`/`best_eclass_term`/`nth`). This precedence is essentially forced by reading which symbol introduces which in the rules — it's not an extra assumption smuggled in, but a direct reflection of the given rewrite system's call graph. That keeps the proof within the boundary of "derivable from the given syntax and rules," as requested, rather than importing an external measure that would need independent justification.

**In short:** the rules have a clean "recursive call decreasing one counter argument, with everything else just structural repackaging" shape, and LPO is the standard, minimal-assumption tool purpose-built for exactly that pattern — so I reached for it first, and it worked without needing any fallback (like RPO with multiset status, or manual well-founded induction on a custom measure).
