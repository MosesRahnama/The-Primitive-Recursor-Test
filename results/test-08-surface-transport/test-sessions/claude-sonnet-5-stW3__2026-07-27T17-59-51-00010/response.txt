### Step 1: `f0` is addition — terminates trivially

- `f0(v0,c0) -> v0`: RHS is a proper subterm of LHS. Strict decrease under any order with the subterm property.

### Step 2: `f3` is predecessor — terminates trivially

### Step 3: `f2` is multiplication built from `f0` — terminates using Step 1

### Step 4: Why a *flat* order fails on rule 8, and what actually saves termination

Rule 8: `f4(f1(v0)) -> f2(f4(f3(f1(v0))), f1(v0))`.

Syntactically, `f3(f1(v0))` is **larger** than `f1(v0)` (it properly contains it), so no order with the subterm property, and no polynomial interpretation with `f3` monotone, can make the new call `f4(f3(f1(v0)))` "smaller" than `f4(f1(v0))` at the syntactic level. This is exactly the point where a naive simplification-order proof breaks.

The resolution is semantic, and it is fully justified by Step 2 (already proved from the rules alone): whenever `v0` is built only from `f1/c0` (the only case in which `f3(f1(v0))` can ever again match rule 8, since `f3`'s rules only fire on `f1(f1(_))`/`f1(c0)` shapes and otherwise the term is a normal form that can never再 present an `f1(_)` head to refire rule 8), the terminating subsystem `f3` computes `f3(f1(v0))` down to the **strict predecessor** `v0` (fewer `f1`-layers than `f1(v0)`).
