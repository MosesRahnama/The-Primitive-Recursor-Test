A completion cannot exist for all three `sorry` cases as written: the `R_rec_succ` decrease statement is false for the current definition of `mu`.

The issue is that the `mu s` summand in

```lean
mu (recDelta b s (delta n))
  = omega0 ^ (mu (delta n) + mu s + 6) + ...
```

can absorb the extra ordinal contribution from `mu (delta n)`. Consequently, the source and recursive-call exponents can coincide, while the `app` wrapper then makes the reduct larger.

For example, take:

```lean
b := void
n := void
s := delta (delta void)
```

Writing `x := mu s`, one has:

```text
mu (delta void) = ω^5 + 1
x = ω^5 * (ω^5 + 2) + 1
```

and therefore, since `x` has leading term `ω^10`,

```text
(mu (delta void) + x + 6) = x + 6.
```

Thus both the source and the recursive subterm have the same leading exponent:

```text
mu (recDelta void s (delta void))
  = ω^(x + 6) + ω + 1

mu (recDelta void s void)
  = ω^(x + 6) + ω + 1.
```

But the reduct has an `omega0 ^ 2` multiplier around that recursive subterm:

```text
mu (app s (recDelta void s void))
  = ω^3 * (x + 1)
    + ω^2 * (ω^(x + 6) + ω + 2)
    + 1
  = ω^(x + 6) + ω^3 + ...,
```

which is strictly greater than

```text
ω^(x + 6) + ω + 1.
```

Hence:

```text
¬ mu (app s (recDelta b s n)) < mu (recDelta b s (delta n))
```

for this instance.

So the `R_rec_succ` branch cannot be filled without changing `mu` (or changing the reduction rule).

The `R_eq_refl` branch, independently, has the simple skeleton:

```lean
| _, _, Step.R_eq_refl a => by
    simp [mu]
    exact add_pos_right _ one_pos
```

If `simp` leaves the goal in a slightly different positivity form, the already-used style also works:

```lean
| _, _, Step.R_eq_refl a => by
    simp [mu]
    exact Ordinal.pos_iff_ne_zero.mpr (by
      apply ne_of_gt
      exact add_pos_right _ one_pos)
```

For `R_eq_diff`, the intended proof shape is reasonable, but it depends on a collection of ordinal-arithmetic comparison lemmas. Structurally it would look like this:

```lean
| _, _, Step.R_eq_diff a b => by
    simp [mu]
    -- Goal:
    -- ω^4 * (ω^3 * (mu a + 1) + ω^2 * (mu b + 1) + 1 + 1) + 1
    --   < ω^(mu a + mu b + 9) + 1

    have h_main :
        omega0 ^ (4 : Ordinal) *
            (omega0 ^ (3 : Ordinal) * (mu a + 1) +
             omega0 ^ (2 : Ordinal) * (mu b + 1) + 1 + 1)
          < omega0 ^ (mu a + mu b + (9 : Ordinal)) := by
      -- Establish separate bounds for the two summands inside the
      -- parentheses, then absorb them below ω^(mu a + mu b + 9).
      --
      -- Typical intermediate goals:
      --
      --   ω^4 * (ω^3 * (mu a + 1))
      --     < ω^(mu a + mu b + 9)
      --
      --   ω^4 * (ω^2 * (mu b + 1))
      --     < ω^(mu a + mu b + 9)
      --
      -- and a bound for the finite tail.
      --
      -- The key ordinal fact needed is that the exponent
      -- `mu a + mu b + 9` dominates the finite tower levels 7 and 6
      -- occurring after distributing the left multiplication.
      sorry

    exact lt_of_lt_of_le h_main (le_add_right _ _)
```

A more robust proof of `R_eq_diff` would likely first prove a reusable bounding lemma, schematically:

```lean
lemma finite_tower_mul_lt_big_opow
    (x y : Ordinal) :
    omega0 ^ (4 : Ordinal) *
        (omega0 ^ (3 : Ordinal) * (x + 1) +
         omega0 ^ (2 : Ordinal) * (y + 1) + 2)
      < omega0 ^ (x + y + (9 : Ordinal)) := by
  sorry
```

and then use it directly:

```lean
| _, _, Step.R_eq_diff a b => by
    simp [mu]
    have h :=
      finite_tower_mul_lt_big_opow (mu a) (mu b)
    exact lt_of_lt_of_le h (le_add_right _ _)
```

However, this only addresses `R_eq_refl` and `R_eq_diff`. Before `mu_decreases` and `strong_normalization` can be completed, the `recDelta` clause of `mu` must be redesigned so that the ordinal information contributed by `delta n` cannot be swallowed by an arbitrarily large `mu s`.
