There is an important obstruction: the `R_rec_succ` case cannot be completed for the file exactly as written, because the ordinal measure does not strictly decrease in that case for all `s`. So a valid proof skeleton for all three `sorry`s does not exist without changing the measure or the rule statement.

The two other cases are routine / plausible. Here is what can be used for them, followed by the obstruction for `R_rec_succ`.

---

### 1. `eqW a a --> void`

This one should be directly provable by the same positivity pattern used in `R_int_delta`.

```lean
-- eqW a a --> void
| _, _, Step.R_eq_refl a => by
    simp [mu]
    exact Ordinal.pos_iff_ne_zero.mpr (by
      apply ne_of_gt
      exact add_pos_right _ one_pos)
```

Equivalently, if the target after `simp [mu]` is accepted directly as positivity:

```lean
| _, _, Step.R_eq_refl a => by
    simp [mu]
    exact add_pos_right _ one_pos
```

---

### 2. `eqW a b --> integrate (merge a b)`

A reasonable proof skeleton is to isolate the ordinal arithmetic into helper lemmas saying that fixed finite constructor overheads are absorbed by the large exponent `mu a + mu b + 9`.

After `simp [mu]`, the goal is essentially:

```lean
omega0 ^ (4 : Ordinal) *
  (omega0 ^ (3 : Ordinal) * (mu a + 1)
   + omega0 ^ (2 : Ordinal) * (mu b + 1)
   + 1 + 1)
  + 1
<
omega0 ^ (mu a + mu b + (9 : Ordinal)) + 1
```

Skeleton:

```lean
-- eqW a b --> integrate (merge a b)
| _, _, Step.R_eq_diff a b => by
    simp [mu]

    let C : Ordinal := mu a + mu b

    -- First bound the merge payload below omega^(C + 4).
    have h_merge_core :
        omega0 ^ (3 : Ordinal) * (mu a + 1)
        + omega0 ^ (2 : Ordinal) * (mu b + 1)
        + 1 + 1
          < omega0 ^ (C + (4 : Ordinal)) := by
      -- Skeleton:
      --
      -- 1. Show the left merge component is below omega^(C + 4):
      --      omega^3 * (mu a + 1) < omega^(C + 4)
      --
      -- 2. Show the right merge component is below omega^(C + 4):
      --      omega^2 * (mu b + 1) < omega^(C + 4)
      --
      -- 3. Show the finite `1 + 1` tail is also below omega^(C + 4).
      --
      -- 4. Use additively principal-ness of omega-powers:
      --      if x < omega^E and y < omega^E, then x + y < omega^E.
      --
      -- Relevant imported material is likely from
      -- `Mathlib.SetTheory.Ordinal.Principal`.
      sorry

    -- Multiplying by omega^4 still stays below omega^(C + 9).
    have h_integrate_core :
        omega0 ^ (4 : Ordinal) *
          (omega0 ^ (3 : Ordinal) * (mu a + 1)
           + omega0 ^ (2 : Ordinal) * (mu b + 1)
           + 1 + 1)
          < omega0 ^ (C + (9 : Ordinal)) := by
      -- Skeleton:
      --
      -- Use monotonicity of multiplication on the right:
      --
      --   omega^4 * merge_core
      --     < omega^4 * omega^(C + 4)
      --     = omega^(4 + (C + 4))
      --
      -- Then prove the finite-overhead inequality:
      --
      --   4 + (C + 4) < C + 9
      --
      -- and conclude by strict monotonicity of omega-exponentiation.
      have hmul :
          omega0 ^ (4 : Ordinal) *
            (omega0 ^ (3 : Ordinal) * (mu a + 1)
             + omega0 ^ (2 : Ordinal) * (mu b + 1)
             + 1 + 1)
            < omega0 ^ (4 : Ordinal) * omega0 ^ (C + (4 : Ordinal)) := by
        -- strict monotonicity of right multiplication by positive omega^4
        -- using `h_merge_core`
        sorry

      have hpow :
          omega0 ^ (4 : Ordinal) * omega0 ^ (C + (4 : Ordinal))
            = omega0 ^ ((4 : Ordinal) + (C + (4 : Ordinal))) := by
        -- omega^x * omega^y = omega^(x + y)
        simpa using (opow_add omega0 (4 : Ordinal) (C + (4 : Ordinal))).symm

      have hexp :
          (4 : Ordinal) + (C + (4 : Ordinal)) < C + (9 : Ordinal) := by
        -- finite ordinal arithmetic:
        -- for finite C this is ordinary arithmetic;
        -- for infinite C the leading finite `4 +` is absorbed.
        sorry

      calc
        omega0 ^ (4 : Ordinal) *
            (omega0 ^ (3 : Ordinal) * (mu a + 1)
             + omega0 ^ (2 : Ordinal) * (mu b + 1)
             + 1 + 1)
            < omega0 ^ (4 : Ordinal) * omega0 ^ (C + (4 : Ordinal)) := hmul
        _ = omega0 ^ ((4 : Ordinal) + (C + (4 : Ordinal))) := hpow
        _ < omega0 ^ (C + (9 : Ordinal)) := by
          -- strict monotonicity of omega-exponentiation
          sorry

    -- Finally, convert `core < omega^E` into `core + 1 < omega^E + 1`.
    have hsucc :
        omega0 ^ (4 : Ordinal) *
          (omega0 ^ (3 : Ordinal) * (mu a + 1)
           + omega0 ^ (2 : Ordinal) * (mu b + 1)
           + 1 + 1)
          + 1
          ≤ omega0 ^ (C + (9 : Ordinal)) := by
      -- from `h_integrate_core : core < omega^E`
      -- use successor characterization: core + 1 ≤ omega^E
      exact succ_le_iff.mpr h_integrate_core

    exact lt_of_le_of_lt hsucc (lt_add_one _)
```

### 3. `recDelta b s (delta n) --> app s (recDelta b s n)` cannot be proved as stated

The intended argument in the comment says that

```lean
mu (delta n) + mu s + 6
```

dominates the exponent appearing in `mu (recDelta b s n)`. But ordinal addition is not commutative, and the leading contribution from `mu (delta n)` can be swallowed by a sufficiently large `mu s`.

A concrete counterexample shape is:

```lean
b := void
n := void
s := delta (delta void)
```

Then:

```lean
mu (delta void) = omega0 ^ 5 + 1
```

and

```lean
mu s = mu (delta (delta void))
     = omega0 ^ 5 * (omega0 ^ 5 + 2) + 1
```

so `mu s` has leading term `omega0 ^ 10`. Therefore the smaller prefix `mu (delta void) = omega0 ^ 5 + 1` is absorbed when added on the left:

```lean
mu (delta void) + mu s + 6 = mu s + 6
```

Thus the leading exponent of

```lean
mu (recDelta void s (delta void))
```

is the same as the leading exponent of

```lean
mu (recDelta void s void)
```

Namely, if

```lean
Ω := omega0 ^ (mu s + 6)
```

then both contain the leading term `Ω`.

More explicitly:

```lean
mu (recDelta void s (delta void)) = Ω + omega0 + 1
mu (recDelta void s void)         = Ω + omega0 + 1
```

But the reduct is

```lean
app s (recDelta void s void)
```

whose measure contains

```lean
omega0 ^ 2 * (mu (recDelta void s void) + 1)
```

That contributes at least

```lean
Ω + omega0 ^ 3
```

because the outer `omega0 ^ 2 *` shifts the tail `omega0` to `omega0 ^ 3`, while the leading `Ω` is not made smaller. Hence:

```lean
mu (app s (recDelta void s void))
  > Ω + omega0 + 1
  = mu (recDelta void s (delta void))
```

So the required inequality is reversed for this instance.

Therefore the `R_rec_succ` case has no valid Lean proof with the measure `mu` as currently defined. The measure would need to be changed, for example by arranging the recursion exponent so that the counter contribution cannot be swallowed by `mu s`, e.g. putting `mu s` before the counter contribution or adding a larger non-swallowable overhead.
