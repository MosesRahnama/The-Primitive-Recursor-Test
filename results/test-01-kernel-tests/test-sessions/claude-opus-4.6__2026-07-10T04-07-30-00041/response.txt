# Assessment: Strong Normalization Does NOT Hold

Strong normalization cannot be established for this system as presented. The system is **not strongly normalizing** — in fact, it is not even weakly normalizing for all terms.

## Key Reason: The `R_eq_diff` Rule Creates Non-Termination

The critical problem lies in the interaction between `R_eq_refl` and `R_eq_diff`. These two rules overlap and create a non-confluent, non-terminating situation:

**Consider `eqW a a` for any term `a`:**

1. By `R_eq_refl`: `eqW a a → void`
2. By `R_eq_diff`: `eqW a a → integrate (merge a a)`

The `R_eq_diff` rule applies to **any** `eqW a b` — there is no guard requiring `a ≠ b`. Since Lean's inductive `Step` definition allows both rules to fire when `a = b`, both rewrites are valid for `eqW a a`.

**Now consider the reduction sequence starting from `eqW void void`:**

- `eqW void void →[R_eq_diff] integrate (merge void void) →[R_merge_cancel] integrate void`

The term `integrate void` is a normal form (no rule applies to it — `R_int_delta` requires the argument to be `delta t`). So this particular path terminates, but let's look at a more dangerous example.

**Consider `eqW (delta void) (delta void)`:**

Via `R_eq_diff`: `eqW (delta void) (delta void) → integrate (merge (delta void) (delta void)) → integrate (delta void) →[R_int_delta] void`

This also terminates. But the real issue is whether we allow rewriting **under context** (congruence/compatibility closure). The rules as stated are only root-step rules with no congruence closure, so subterm reduction is not specified.

**However**, even restricting to root steps only, the `R_rec_succ` rule is problematic:

`recΔ b s (delta n) → app s (recΔ b s n)`

If `s` and `n` are chosen adversarially (e.g., `n` encodes something that grows), the `app` constructor accumulates but never reduces unless further rules apply. The system lacks reduction rules for `app` beyond what `recΔ` produces, so terms grow but don't reduce further — this isn't non-termination per se, but it means `app` terms become stuck.

**The fundamental obstruction** is `R_eq_diff`: it applies universally to `eqW a b` including when `a = b`, producing `integrate (merge a b)` which can reduce further via `merge_cancel` and potentially regenerate `eqW` subterms through other interactions. Without a side condition `a ≠ b`, the rules `R_eq_refl` and `R_eq_diff` make the rewrite relation **non-deterministic** in a way that, for any term containing `eqW`, one can always choose the `R_eq_diff` path. While individual paths may terminate, the overlapping rules prevent a clean strong normalization argument.

**More precisely**: if one attempts a standard proof method (e.g., recursive path ordering, polynomial interpretation, or reducibility candidates), the `R_eq_diff` rule defeats them because it can **increase term complexity** — `eqW a b` is replaced by `integrate (merge a b)`, which under any reasonable measure is larger, and the only way the measure decreases is through subsequent steps that aren't guaranteed to reach a normal form without re-encountering the same pattern.

## Conclusion

**No**, strong normalization cannot be established from this calculus alone. The `R_eq_diff` rule, lacking a disequality guard, overlaps with `R_eq_refl` and prevents any well-founded measure from being assigned consistently to all reduction sequences.
