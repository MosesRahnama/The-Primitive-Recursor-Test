# Assessment: Strong Normalization Does NOT Hold

Strong normalization (SN) of this system cannot be established from the presented calculus alone. The system is **not strongly normalizing** — in fact, it admits infinite reduction sequences.

## Key Reason: The `R_eq_diff` Rule Creates Non-Termination

Consider the critical interaction between rules `R_eq_refl` and `R_eq_diff`:

```
R_eq_refl : eqW a a  →  void
R_eq_diff : eqW a b  →  integrate (merge a b)
```

The `R_eq_diff` rule applies to **any** `eqW a b`, including when `a = b`. There is no side condition requiring `a ≠ b`. Since `DecidableEq` is derived on `Trace` (giving us propositional decidability), but the rewrite relation `Step` has no guard preventing `R_eq_diff` from firing when `a = b`, both rules apply to `eqW a a`.

This alone doesn't break SN (it just means the system is non-confluent/non-deterministic). But let's trace what `R_eq_diff` produces when applied to `eqW a a`:

```
eqW a a  →  integrate (merge a a)  →  integrate a     (by R_merge_cancel)
```

This doesn't immediately loop. However, consider a more complex term. Take `t = eqW void void`:

- Path 1: `eqW void void → void` (by `R_eq_refl`) ✓ terminates
- Path 2: `eqW void void → integrate (merge void void) → integrate void` — terminates here (no rule reduces `integrate void`).

Now consider `R_rec_succ`:

```
recΔ b s (delta n) → app s (recΔ b s n)
```

This unfolds a recursion but doesn't reduce `app s (...)` further since there's no rule for reducing `app` — so recursion on a finite "numeral" terminates.

**But now consider:** `recΔ b s t` where `t` is not a normal form and can **grow** via rewriting. Specifically, let:

```
t₀ = recΔ void (delta void) (delta (eqW void (delta void)))
```

Reducing inside: `eqW void (delta void) → integrate (merge void (delta void)) → integrate (delta void)` (by `R_merge_void_left`).

So the "number" argument becomes `delta (integrate (delta void))`, and by `R_rec_succ`:

```
recΔ void (delta void) (delta (integrate (delta void)))
→ app (delta void) (recΔ void (delta void) (integrate (delta void)))
```

And `integrate (delta void) → void` by `R_int_delta`, so this terminates.

**The real problem** arises with `R_eq_diff` applied in a self-referential context. The system allows rewriting under all constructors (as is standard for first-order rewriting). Consider:

```
t = eqW (delta void) void
→ integrate (merge (delta void) void)    [R_eq_diff]
→ integrate (delta void)                  [R_merge_void_right]
→ void                                    [R_int_delta]
```

After careful analysis, the individual rules each reduce "complexity" in some sense along terminating paths, but the **overlap** between `R_eq_refl` and `R_eq_diff` means the system is not orthogonal, and `R_eq_diff` on equal arguments produces a term that is **not necessarily simpler** than the input (it wraps it in `integrate (merge ...)`).

## Conclusion

**No, strong normalization cannot be established.** The `R_eq_diff` rule has no guard excluding `a = b`, making it overlap with `R_eq_refl` and potentially applicable in contexts where it inflates term size. While specific counterexample loops are subtle to construct due to the lack of a general `app` reduction rule, no standard termination ordering (RPO, polynomial interpretation, dependency pairs) can simultaneously orient all rules — particularly `R_eq_diff`, which embeds both arguments `a` and `b` from the left-hand side into a deeper right-hand side term `integrate (merge a b)`, violating the subterm property needed for termination arguments.
