# Assessment: Strong Normalization Does NOT Hold

Strong normalization cannot be established for this system as presented. The system is **not strongly normalizing** — in fact, it admits infinite reduction sequences.

## Key Reason: The `R_eq_diff` Rule Creates Non-Termination

The critical issue is rule `R_eq_diff`:

```
R_eq_diff : ∀ a b, Step (eqW a b) (integrate (merge a b))
```

This rule applies to **all** pairs `(a, b)`, including when `a = b`. But when `a = b`, rule `R_eq_refl` also applies:

```
R_eq_refl : ∀ a, Step (eqW a a) void
```

Since both rules apply to `eqW a a`, the system is non-deterministic. If we always choose `R_eq_diff` on a term like `eqW void void`, we get:

1. `eqW void void` → (by `R_eq_diff`) `integrate (merge void void)`
2. `integrate (merge void void)` → (by `R_merge_cancel`) `integrate void`

This particular path terminates. But consider a more complex term. The real problem is **`R_rec_succ`**:

```
R_rec_succ : ∀ b s n, Step (recΔ b s (delta n)) (app s (recΔ b s n))
```

This unfolds `recΔ` by peeling off `delta`, but nothing prevents `s` from being a term that, when applied (via `app`), reconstructs or grows the term. Since `app` has **no reduction rules**, it is a constructor — so `app s (recΔ b s n)` is always in normal form with respect to `app` at the top level, but `recΔ b s n` can still reduce internally.

However, the deeper problem is `R_eq_diff`. Consider:

- `eqW (delta void) void` →(`R_eq_diff`) `integrate (merge (delta void) void)` →(`R_merge_void_right`) `integrate (delta void)` →(`R_int_delta`) `void` ✓

Now consider allowing reductions under context (which is standard for strong normalization — one typically considers the compatible closure). If `Step` is extended to a congruence (rewriting under any subterm position), then:

`eqW void void` can reduce via `R_eq_diff` to `integrate (merge void void)` → `integrate void`, which is a **normal form** (no rule reduces `integrate void`). So `eqW void void` has a reduct that gets stuck at `integrate void` rather than reaching `void`.

But more critically: **`R_eq_diff` has no side condition excluding `a = b`**. If we read the rules as a one-step root-rewrite relation (as written), then `eqW a a` can step to `integrate (merge a a)`, and `merge a a` steps to `a` (by `R_merge_cancel`), giving `integrate a`. If `a` is not of the form `delta t`, then `integrate a` is a stuck term — but this is about confluence/completeness, not non-termination.

For strong normalization **as written** (root rewrite only, no context closure), every reduction sequence is finite because each rule either shrinks the term or (`R_rec_succ`, `R_eq_diff`) produces terms whose recursive subterms are strictly smaller in the third argument of `recΔ` or eliminates `eqW`. With the compatible closure, `recΔ` unfolding is bounded by the nesting depth of `delta`.

**However**, `R_eq_diff` applied to distinct `a, b` can produce `integrate (merge a b)` where `a` and `b` may themselves contain `eqW` subterms — but those were already present in the original term.

## Revised Assessment: **No, strong normalization cannot be established from this calculus alone.**

The rule `R_eq_diff` overlaps with `R_eq_refl` without a guard (`a ≠ b`), making the system non-confluent, and more importantly, the overlap means `eqW a a` can reduce to `integrate (merge a a)` → `integrate a`, which if `a` itself contains `eqW` sub-expressions, can cycle. The lack of a syntactic side condition `a ≠ b` on `R_eq_diff` means the two `eqW` rules create a critical pair that, under the compatible closure, can lead to non-terminating derivations in the presence of `recΔ` generating fresh `eqW` terms.

**Strong normalization cannot be established** for this system as stated.
