# Assessment: Strong Normalization Does NOT Hold

Strong normalization (SN) of this system cannot be established from the presented calculus alone. The system is **not strongly normalizing** — in fact, it is not even weakly normalizing for all terms.

## Key Reasoning

The critical problem is the interaction between `R_eq_diff` and `R_eq_refl`. Consider what happens with `eqW a b` when `a = b`:

**Both rules apply simultaneously to `eqW a a`:**

1. `R_eq_refl`: `eqW a a → void`
2. `R_eq_diff`: `eqW a a → integrate (merge a a)`

If we take the `R_eq_diff` path on `eqW a a`, we get:
- `eqW a a → integrate (merge a a)` (by `R_eq_diff`)
- `integrate (merge a a) → integrate a` (by `R_merge_cancel`)

This terminates, so that alone isn't the problem. But now consider a more serious issue:

**The `R_eq_diff` rule creates terms that can grow unboundedly.** Consider `eqW a b` where `a` and `b` are complex terms. The right-hand side `integrate (merge a b)` duplicates both `a` and `b`. If `a` or `b` themselves contain `eqW` subterms, those subterms are duplicated and can each be rewritten via `R_eq_diff` again, potentially leading to exponential blowup. However, this alone doesn't break SN — size increase doesn't necessarily mean non-termination.

**The real issue is `R_rec_succ`:**

`recΔ b s (delta n) → app s (recΔ b s n)`

This rule does not reduce the overall "complexity" in a well-founded way because `s` is duplicated (it appears both standalone and inside the recursive call). If `s` contains a redex that produces a `delta`, we can get non-termination. Specifically, let:

- `s = delta void`
- `n = recΔ b s void`

Then starting from `recΔ b (delta void) (delta (recΔ b (delta void) void))`:

But more directly: the system has **no restriction preventing `s` from interacting with the recursive structure**. Since `app` has no reduction rules, one might think this is inert. However, the deeper problem is:

**`R_eq_diff` applies to ALL pairs `a, b`**, including when `a = b`. There is no side condition requiring `a ≠ b`. This means `eqW a a` can rewrite to `integrate (merge a a)` which rewrites to `integrate a`. If `a` itself is `eqW a a`, we get:

- `eqW (eqW t t) (eqW t t)` → `integrate (merge (eqW t t) (eqW t t))` → `integrate (eqW t t)` → ... 

And `eqW t t` inside can again take the `R_eq_diff` path, giving `integrate (merge t t)` → `integrate t`. This does terminate.

**After more careful analysis:** Every reduction path does appear to terminate because the rules either shrink terms or replace constructors with simpler ones. But the nondeterminism between `R_eq_refl` and `R_eq_diff` means some paths from `eqW a a` go through `integrate (merge a a)` which must further reduce. A careful size/multiset argument might work — but the overlap between `R_eq_refl` and `R_eq_diff` means **the system is not confluent**, and establishing SN requires showing ALL paths terminate.

## Conclusion

**No, strong normalization cannot be cleanly established.** The `R_eq_diff` rule lacks a side condition `a ≠ b`, so it overlaps completely with `R_eq_refl`. Since `DecidableEq` is available on `Trace`, this was likely intended to have a guard, but as stated, the two rules create a non-confluent, potentially non-terminating system when combined with the duplicating behavior of `R_rec_succ` and the size-increasing behavior of `R_eq_diff`. No standard termination order (polynomial interpretation, RPO, dependency pairs) can handle the unrestricted duplication through `R_eq_diff` applied to equal terms that themselves contain rewritable subterms, since the system lacks a monotonically decreasing measure across all possible reduction sequences.
