| R_eq_diff : ∀ a b, Step (eqW a b) (integrate (merge a b))

```lean
| R_eq_refl : ∀ a, Step (eqW a a) void

This creates a non-confluence issue, but more importantly for normalization, consider what happens with `R_eq_diff` when `a = b`:

- `eqW a a` can reduce via `R_eq_diff` to `integrate (merge a a)`

This path terminates, but the real problem is the **`R_rec_succ` rule**:

| R_rec_succ : ∀ b s n, Step (recΔ b s (delta n)) (app s (recΔ b s n))
```

The term `app s (recΔ b s n)` contains `recΔ b s n` as a subterm, and there is **no reduction rule for `app`**. The `app` constructor is inert—it never reduces.

More fundamentally: the `R_eq_diff` rule has **no guard preventing it from firing when `a = b`**. Since both `R_eq_refl` and `R_eq_diff` apply to `eqW a a`, and `DecidableEq` is only used at the meta-level (for the `deriving` clause), the rewrite relation `Step` itself treats these as two separate applicable rules.

The `R_eq_diff` overlap with `R_eq_refl` breaks confluence but not termination. Each rule either reduces structural size or decreases a bounded quantity.
