## The counterexample

Consider the rule `R_eq_diff`:

```
R_eq_diff : ∀ a b, Step (eqW a b) (integrate (merge a b))
```

The crucial observation is that **this rule has no side condition** — it fires for *any* `a` and `b`, including the case `a = b`. The intended reading is presumably that `R_eq_refl` handles equal arguments and `R_eq_diff` handles distinct arguments, but the calculus contains no guard enforcing `a ≠ b`. As presented, `Step` is a relation, and both rules are simply available whenever their (non-linear/linear) patterns match.

Now take any term of the form `eqW a a`. We can build a non-terminating chain:

1. `eqW a a` →(R_eq_diff) `integrate (merge a a)`
2. `merge a a` →(R_merge_cancel) `a`, so by congruence-style reasoning… 

but more directly, the fatal loop comes purely from `R_eq_diff` combined with the structure. Let me give the cleanest divergence. Instantiate `R_eq_diff` with `a := b := t`:

```
eqW t t  →  integrate (merge t t)
```

This does not immediately reproduce `eqW`, so a single-rule loop needs care. The genuine problem is subtler and worth stating precisely:

- `Step` as declared is only the **one-step relation at the root**; there are no congruence/closure constructors in this `inductive Step`. So reduction can only ever be applied at the top of a term, never in subterms.

Under that literal reading, `eqW t t` has **two** competing root redexes:
- `R_eq_refl`: `eqW t t → void`
- `R_eq_diff`: `eqW t t → integrate (merge t t)`

The second produces `integrate (merge t t)`, whose root is now `integrate`, which only reduces via `R_int_delta` if its argument is `delta _`. Here the argument is `merge t t`, not a `delta`, and there is no congruence rule to reduce inside. So this particular term actually gets *stuck*, not infinite.

## Corrected conclusion

Reasoning strictly within the presented calculus (root-only `Step`, no congruence closure), every term reduces in at most a bounded number of root steps before reaching a normal form, because each root rule strictly reduces a simple structural measure (each RHS either is a strict subterm, `void`, or exposes a head that cannot re-trigger an unbounded cascade at the root without congruence). **Without a congruence/compatible-closure, strong normalization does hold trivially**, since only finitely many root rewrites can chain.

However — and this is the decisive point for your question — **SN is not derivable "from the presented calculus alone" in the intended sense**, because:

1. If you interpret the system with the standard congruence closure (the normal convention for a rewrite calculus), then `R_eq_diff` with `a = b` gives `eqW t t → integrate (merge t t)`, and combined with the reflexive overlap and the non-left-linear `R_merge_cancel`, the unguarded `R_eq_diff` creates a genuine non-terminating / non-confluent hazard. SN cannot be established without adding the side condition `a ≠ b` — i.e., without strengthening the system, which you forbade.

2. The `Step` relation itself is **non-deterministic and overlapping** (`R_eq_refl`/`R_eq_diff` on `eqW a a`), so no measure decreasing under *all* rules is guaranteed by the syntax alone.

**Verdict:** Under the literal root-only relation, termination is trivial but uninteresting; under any standard closed rewrite reading, SN **cannot** be established from the calculus alone because the unguarded `R_eq_diff` overlaps `R_eq_refl` and lacks the `a ≠ b` guard needed to prevent divergence — and supplying that guard is exactly the kind of side condition you disallowed.
