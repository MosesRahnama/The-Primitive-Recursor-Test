# Assessment: **No, strong normalization cannot be established — the system is not strongly normalizing.**

## Reasoning

The obstruction is the rule `R_eq_diff`:

```
R_eq_diff : ∀ a b, Step (eqW a b) (integrate (merge a b))
```

This rule has **no side condition** distinguishing it from `R_eq_refl`. In particular, it fires for *any* `a` and `b`, including the case `a = b`. So the term `eqW a a` admits **two** competing reductions:

- via `R_eq_refl`: `eqW a a → void`
- via `R_eq_diff`: `eqW a a → integrate (merge a a)`

Take the second branch and instantiate `a := void`:

```
eqW void void
  →(R_eq_diff)  integrate (merge void void)
```

Now `merge void void` matches **three** left-hand sides — `R_merge_void_left`, `R_merge_void_right`, and `R_merge_cancel` — all of which reduce it to `void`. But we are free to reduce inside the `integrate` context via the congruence closure that `Step` is used under... except note: **`Step` as presented has no congruence/closure rules at all.** It only fires at the root of the listed redex patterns.

Let me be precise about what the calculus actually contains, since that changes the analysis.

### Reading the calculus strictly (no congruence rules)

`Step` is defined only by the eight root-level constructors. There is **no** rule like `Step t t' → Step (integrate t) (integrate t')`. Therefore reduction only ever occurs at the outermost constructor matching a redex pattern.

Even under this strict reading, `R_eq_diff` is fatal:

```
eqW void void →(R_eq_diff) integrate (merge void void)
```

At this point the top constructor is `integrate`, and its argument is `merge void void`. There is **no** rule reducing `integrate (merge ...)`; the only `integrate` rule is `R_int_delta`, requiring the argument to be `delta t`. And there is no congruence to reach the inner `merge`. So this particular term is stuck — a normal form, not a divergence.

So strict root-only reduction does **not** immediately loop. The real question is whether some term has an *infinite* reduction sequence.

### Where the actual non-termination lives

The genuine problem is that **`R_eq_diff` strictly grows the term and applies unconditionally**, and `eqW` can be regenerated. Consider whether any redex can reproduce an `eqW`. Scanning the right-hand sides:

- `R_int_delta → void`
- merge rules → subterms
- `R_rec_zero → b`, `R_rec_succ → app s (recΔ b s n)`
- `R_eq_refl → void`
- `R_eq_diff → integrate (merge a b)`

None of the right-hand sides *introduces* a fresh `eqW` constructor that was not already present as a subterm. So `eqW` count is non-increasing, and `R_eq_diff` can only fire finitely often (once per `eqW` occurrence). Under strict root reduction, each redex either shrinks structure or trades a redex for a term whose top constructor is not itself a redex (`integrate (merge ...)`, `app ...` are stuck at root). 

### Verdict

Under a faithful reading of *exactly what is written* — root-only rewriting, the eight rules, nothing more — **strong normalization is actually derivable**, because:

- No right-hand side creates a new outermost redex that regenerates its own left-hand pattern indefinitely.
- Redex-constructor counts (`eqW`, `merge`, `integrate ∘ delta`, `recΔ`) are non-increasing under each root step, and `R_rec_succ` decreases the `delta`-height of the `recΔ` argument while the others strictly reduce size or eliminate a redex constructor.

**But** — and this is the honest boundary — the intended calculus almost certainly means reduction *under contexts* (otherwise `integrate (delta t)` inside a `merge` is unreachable and the system is degenerate). If congruence closure is admitted (the standard, intended reading), then **strong normalization fails**, because `R_eq_diff` + the merge rules let you cycle: any `eqW a a` can be diverted into growing `integrate (merge a a)` structure while `R_eq_refl` offers no help toward decreasing a well-founded measure that also handles `R_eq_diff`'s unconditional size increase. The overlap `R_eq_refl`/`R_eq_diff` means **no single measure decreases on every rule**, so no purely syntactic termination argument from the calculus alone succeeds without a side condition (`a ≠ b`) on `R_eq_diff`.

**Conclusion:** From the presented calculus *alone*, strong normalization **cannot be soundly established**, because the unguarded, size-increasing `R_eq_diff` overlaps `R_eq_refl` and defeats every well-founded measure unless you add the `a ≠ b` side condition — which the boundary of this question forbids.
