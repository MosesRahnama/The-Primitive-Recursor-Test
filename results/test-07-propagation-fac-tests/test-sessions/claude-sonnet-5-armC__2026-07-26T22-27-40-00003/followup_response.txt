I picked that combination for fairly concrete diagnostic reasons, not out of habit — let me walk through the actual decision process.

**Step 1: Try the cheapest tool first (simplification orders).**
My first instinct for any first-order TRS without AC or built-in arithmetic is to check whether a simple syntactic order — LPO, RPO, or a linear polynomial interpretation — can orient every rule. These are cheap to check and, if they work, they give termination *and* the stronger property of simple termination for free. So I tried to orient the rule set that way first.

**Step 2: Locate exactly where this fails.**
Every rule oriented fine except `fac(s(x)) -> times(fac(p(s(x))), s(x))`. The obstruction is specific and structural: any simplification order needs the recursive argument `p(s(x))` to be "smaller" than `s(x)` in a way compatible with the subterm property, but `p(s(x))` is *syntactically bigger* than `s(x)` (it contains it as a proper subterm plus one more symbol). This isn't a matter of picking a cleverer precedence — it's a genuine mismatch between the syntactic shape of the recursive call and any order with the subterm property. That's the signature of a "terminating but not simply terminating" system (the classic example being predecessor-based recursion, e.g. Ackermann-style or fac-with-truncated-predecessor systems), so once I recognized this pattern I knew simplification orders were dead ends and I shouldn't waste more effort tuning precedences.

**Step 3: Pick a method designed exactly for that failure mode.**
Once the obstruction is "the recursive argument isn't syntactically smaller, only *semantically* smaller after unfolding p's own rules," there are really two standard escape routes in the term-rewriting termination toolbox:

- **Semantic labelling**: decorate function symbols with values from a model derived from the rules themselves (here, interpreting `p` as truncated predecessor and `s` as successor), turning the semantic decrease into a syntactic one after labelling, so a simplification order can then finish the job on the labelled system.
- **Dependency pairs with usable rules**: this framework is specifically built to let you *use the defining rules of auxiliary functions* (`p`, `s`'s rules) as side knowledge when comparing recursive call arguments, rather than needing a single global simplification order over the whole system.

I picked these two because they're the standard, well-established techniques whose entire purpose is to handle exactly this "non-simply-terminating but terminating" situation — they don't require importing any outside axiom about natural numbers; the interpretation/usable rules are constructed *from the rules given* (the `p(s(s(x))) -> s(p(s(x)))`/`p(s(0))->0` equations literally define truncated predecessor, so the semantic model is licensed by the rule set itself, not smuggled in from outside).
