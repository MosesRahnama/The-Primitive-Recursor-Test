I chose it because the rules essentially *announce* the termination argument themselves — the cleanest method is the one that follows the shape of the rules rather than fighting it.

**The structure points to size-decrease on the third argument.**

Rule 2 is `F(x, y, S(n)) → G(y, F(x, y, n))`. The `S` constructor is stripped and `n` reappears in the recursive position. That is, by construction, a structural recursion on a Peano numeral. Any termination proof that doesn't exploit this obvious decrease would be obscuring rather than clarifying. The right measure is the one the rule's author already had in mind: the size of the numeral in the third slot.

**Other methods I considered and rejected:**

- **"It's primitive recursive, therefore total."** This is the most natural English-language justification, but it imports an external theorem (every primitive recursive definition terminates). The prompt explicitly forbids that — no object-level assumptions beyond what the rules give you.
- **Polynomial interpretation / matrix interpretation.** I'd have to define a mapping `[[·]] : Term → ℕ` from outside, which counts as importing hidden semantic structure.
- **Dependency pairs (DP framework).** Works in principle, but it requires a separate DP problem whose termination is itself proved by… some other method. For a system this small it adds machinery without adding insight, and one could quibble about whether the DP framework's soundness theorem is an "imported axiom."
- **Recursive/lexicographic path orderings.** These need a chosen *status* for `F` and an argument about argument positions. Doable, but the choice of status and the well-foundedness of the ordering are themselves external results. For a system where the decrease is one line of arithmetic, this is overkill and arguably smuggles in assumptions.

**Why my method stays inside the boundary.**

The argument uses only:

1. The syntax of the given terms (Z and S build the numerals; F and G are the function symbols).
2. Direct inspection of each rule — what pattern it matches, what it produces.
3. The fact that `Z` is not unifiable with `S(n)` (syntactic, immediate from the rules).
4. The well-foundedness of `(<)` on naturals as generated by `Z`/`S` — but this is *given* by the rules themselves: rule 1 names the base case, rule 2 names the step, and `S(n) > n` is visible from the syntax. I didn't import an external fact about ℕ; I read it off the rule shapes.

**The trade-off I'm accepting.**

This method is essentially "do what the programmer obviously did." That's both its strength (it's tight, local, and provable from the rules alone) and its limitation (it works here precisely because the system is well-founded by construction — Rule 2 *looks* like a structural recursion and *is* a structural recursion). A more adversarial rewrite system — one with mutual recursion, permuted arguments, or non-structural decrease — would need a more powerful method, and at that point the constraint "no external assumptions" becomes genuinely binding. For this system, though, the lightweight measure is the honest one: the rules don't pretend to do anything more than they do.
