# Why I chose the Dependency Pair method with a monotone interpretation

## 1. I first tried the cheapest tool and it failed diagnostically, not just practically

My first move was to check whether a plain simplification order (RPO/LPO/KBO) could close the system, since that's the lowest-cost method and works for "most" primitive-recursive-style rewrite systems. Rules 1–7 fell to a simple RPO precedence immediately — no surprises there.

Rule 8 is where it broke, and it broke for a **structural reason**, not just bad luck with a precedence choice:

```
fac(s(x)) -> times(fac(p(s(x))), s(x))
```

Any simplification order satisfies the **subterm property**: `t ⊐ s` whenever `s` is a proper subterm of `t`. To orient rule 8 by comparing the recursive call `fac(s(x))` against `fac(p(s(x)))`, I'd need `s(x) ≻ p(s(x))`. But `s(x)` is a proper subterm of `p(s(x))` (since `p(s(x))` literally contains `s(x)` inside it), so the subterm property forces `p(s(x)) ⊐ s(x)`, i.e. the *opposite* inequality. This isn't a failure of cleverness in picking weights/precedence — **no simplification order can ever orient this rule left-to-right**, by definition of what a simplification order is.

That's a structural obstruction, and it told me I needed a method that doesn't require the reduction to be compatible with the subterm ordering everywhere — only where it matters for actual infinite chains.

## 2. Why Dependency Pairs specifically

The DP framework was built exactly for this situation: rules where the recursive call is "hidden" inside a larger, structurally non-decreasing context (`p(s(x))` growing before shrinking is a classic instance of this — it's the same phenomenon as in `ackermann`-style or "subtraction/predecessor" recursions). DP transforms the question "is every rewrite sequence finite?" into "is every *dependency chain* finite?", and crucially:

- It only demands strict decrease **on cycles of the dependency graph** — i.e., only where recursive calls can actually recur infinitely.
- Non-recursive or transient dependency pairs only need weak decrease.
- This relaxation is exactly what's needed here: `DP6: FAC(s(x)) -> FAC(p(s(x)))` is on a self-loop and does need strict decrease, but I don't need the *whole rule* (including the `times(...)` context) to respect a simplification order.

So DP is the natural escalation once simplification orders are structurally blocked — it's the standard next tool in the termination toolbox, not an exotic choice.

## 3. Why I picked *this* interpretation (factorial/arithmetic semantics) instead of a syntactic order on the DP problem

Once in the DP framework, I still need *some* way to compare terms (a reduction pair). I chose a semantic/arithmetic interpretation rather than a term order (like LPO on the DP problem) because:

- The rules are literally arithmetic (`plus`, `times`, `p`, `fac` as predecessor/factorial), so an interpretation into `(ℕ, ≥)` built from the *actual mathematical meaning* of these operations makes every inequality either an **identity** (rules 1, 6, 7, 8 became equalities) or a **transparent numeric fact** (rules 2–5, and the DP inequalities). This is the most direct way to see *why* the system terminates: it's just tracking that `x! `, `p(x)`, sums and products behave the way arithmetic says they should.
- It handles all four cyclic DPs (`PLUS`, `TIMES`, `P`, `FAC` self-loops) *simultaneously* with one interpretation, rather than needing four separate arguments — a strong indication it's the "right" measure, not a lucky patch.
- It stays entirely within the given signature (no new function symbols, no side conditions) — it's just an ℕ-valued semantics for the existing symbols, satisfying the boundary condition of the question (no smuggled-in extra rules/assumptions).

## 4. Why not other options (size-change, semantic labeling, matrix interpretations)?

I considered these but the polynomial/factorial interpretation was simplest and sufficient:
- **Size-change principle** would work on the DP call graph too, but I'd still need a well-founded measure per argument, which is essentially what the interpretation already gives me, more directly.
- **Matrix interpretations** are a fine generalization but overkill — one scalar interpretation per symbol already closes every rule and every cyclic DP, so there was no need for the added complexity of matrices.

## Summary

I picked DP + monotone interpretation because:
1. Diagnosis: the subterm-property obstruction in rule 8 rules out *all* simplification orders outright, not just my first attempt.
2. DP is the standard, minimal escalation that only requires strict decrease on genuine recursion cycles, matching exactly what rule 8's structure demands.
3. A direct arithmetic interpretation was the natural semantics-respecting reduction pair, closing all 8 rules and all 4 cyclic dependency pairs in one uniform argument, using only the given signature.
