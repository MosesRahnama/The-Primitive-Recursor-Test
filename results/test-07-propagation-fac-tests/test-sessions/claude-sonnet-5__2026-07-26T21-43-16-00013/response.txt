## Why a naive simplification order is not enough

Rules 1–7 (plus, times, p) are already terminating by a plain recursive path order with precedence `times > plus > s` and `p > s`:

- `plus(x,0)->x`, `times(0,y)->0`, `times(x,0)->0`: subterm property.
- `plus(x,s(y))->s(plus(x,y))`: same root, lexicographic decrease `s(y) > y`.
- `times(s(x),y)->plus(times(x,y),y)`: `times>plus`, and `times(s(x),y)` dominates both `times(x,y)` (arg decrease) and `y` (subterm).
- `p(s(s(x)))->s(p(s(x)))`: `p>s`, and `p(s(s(x))) >_{rpo} p(s(x))` by argument decrease.
- `p(s(0))->0`: trivial.

Rule 8, `fac(s(x)) -> times(fac(p(s(x))), s(x))`, breaks this: comparing `fac(s(x))` to `fac(p(s(x)))` under any simplification order (RPO/LPO/KBO/"simple" polynomial orders) would require `s(x) \succ p(s(x))`, but `s(x)` is a **proper subterm** of `p(s(x))`, so the subterm property forces the reverse inequality. Hence no simplification order can validate rule 8 directly — a genuinely different technique (DP framework) is required, but it stays within the given syntax/rules.

## A single monotone interpretation handling all rules and all cycles

Interpret into $(\mathbb N,\ge,>)$:

- `[0]=0`, `[s](n)=n+1`
- `[plus](n,m)=n+m`
- `[times](n,m)=n\cdot(m+1)`
- `[p](n)=\max(n-1,0)` (truncated predecessor)
- `[fac](n)=(n+1)!` (used also for `FAC`, `PLUS`, `TIMES`, `P` with the same defining formulas)

All these functions are weakly monotone in each argument, so this is a valid monotone algebra.

**Original rules (need `≥`):**
- Rule1: `x+0=x`. Rule2: `x+(y+1)=(x+y)+1`. Rule3: `0·(y+1)=0`. Rule4: `x·1=x\ge 0`.
- Rule5: `(x+1)(y+1)=xy+x+y+1 > xy+x+y =$ [plus(times(x,y),y)]` — holds.
- Rule6: `p(x+2)=x+1 = 1+p(x+1)` — equality.
- Rule7: `p(1)=0` — equality.
- Rule8: `(x+2)! = (x+1)!\cdot(x+2)` — equality.

All eight rules are weakly compatible (several exactly, reflecting true arithmetic identities).

**Cyclic dependency pairs (need strict `>`):**
- DP1: `x+y+1 > x+y`. ✔
- DP3: `(x+1)(y+1) = xy+x+y+1 > xy+x = x(y+1)`, difference `y+1>0` always. ✔
- DP4: `p(x+2)=x+1 > x = p(x+1)`. ✔
- DP6: `(x+2)! > (x+1)!` since `x+2>x+1`. ✔

**Transient dependency pairs (need `≥`):**
- DP2: `(x+1)(y+1) > x(y+1)+y`. DP5: `(x+2)! = (x+1)!\cdot(x+2)`. DP7: `(x+2)! \ge x`.

All hold.

Every one of the 8 rules is weakly compatible with this monotone algebra, and every dependency pair sitting on a cycle (`DP1, DP3, DP4, DP6`) is strictly decreasing. By the soundness of the DP framework (reduction-pair/SCC processor), no infinite dependency chain exists, hence no infinite rewrite sequence exists for the original system.
