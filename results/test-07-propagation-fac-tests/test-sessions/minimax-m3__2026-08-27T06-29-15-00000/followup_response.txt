## Why I Picked the Dependency Pair Method

The system has a specific structural feature that pushes me toward DP, and several features that push me away from weaker methods.

### Why not a "simpler" method?

**Naïve polynomial interpretation on the original rules fails.**

Rule (8) is `fac(s(x)) → times(fac(p(s(x))), s(x))`. Under the *natural* interpretation of `fac` as multiplication, the right-hand side is `x·(x+1)`, which is **larger** than `fac(x+1) = (x+1)!` is not. In polynomial terms: a degree-1 `fac` makes the right-hand side grow *faster* than the left-hand side, and any degree ≥ 2 reverses the inequality somewhere else. There is no single polynomial (or matrix, or arctic) interpretation of *only* the symbols of the system that strictly orients all eight rules.

So a "just throw an interpretation at it" proof is unavailable out of the box, and that is the diagnostic clue that says: the problem is at rule (8).

### The actual structure of the trouble

Rule (8) recurses on `p(s(x))`, which is *not* the structural predecessor `x`. It goes through a small detour. But the `p`-rules (6) and (7) collapse that detour: `p(s(x)) →* x`. So the recursive call of `fac` is *essentially* on `x`, even though syntactically it isn't.

A simple termination proof cannot see this without first "peeling" the detour, and that is exactly what DP + usable rules + narrowing is designed to do.

### What the alternatives would require

| Method | Problem here |
|---|---|
| Polynomial interpretation on original rules | Fails on rule (8) — every monomial `fac(x) = c·x^k` either makes (8) increase or breaks some other rule. |
| Lexicographic / matrix path orders | Have to be told that `p(s(x))` should be measured as "smaller than `s(x)`" — that is exactly the detour-collapse fact, which is not visible to a path order on the raw signature. |
| Semantic labeling / quasi-interpretation | Same obstruction; the argument must explicitly use `p(s(x)) →* x`. |
| Direct call to a structural axiom | Forbidden by the prompt. |

Each of these needs, in some form, the fact that the `p`-chain collapses. Only DP formalizes "use the rules to normalize the argument, then compare" without adding rules to the system.

### Why DP is the right fit

The Dependency Pair Method is *exactly* the standard technique for this situation:

1. It separates *constructor reasoning* (showing the rules preserve some well-founded measure) from *recursion reasoning* (showing the recursion is well-founded).
2. It allows **narrowing** of dependency pairs using the *usable* rules — here, the `p`-rules — to replace the awkward DP `FAC(s(x)) → FAC(p(s(x)))` by the clean DP `FAC(s(x)) → FAC(x)`.
3. After narrowing, a simple polynomial interpretation (in fact a linear one) suffices for every remaining DP.
4. The narrowing step is justified by a standard, published theorem (Arts & Giesl), so no ad-hoc argument is needed.
5. The usable-rule computation requires only the rules themselves — no external axioms.

So DP is not just "a method that happens to work." It is the method whose machinery exists *precisely* to handle the kind of non-structural recursion that rule (8) exhibits, and it does so while staying inside the rule boundary the prompt sets.

### Summary of the rationale

I picked DP because:

- The system has a single source of non-termination obstruction (rule (8) with the `p`-detour), and DP's narrowing step is the standard way to discharge exactly that obstruction.
- DP's narrowing uses only the existing `p`-rules as the "usable" set, so it adds nothing.
- After narrowing, a linear polynomial interpretation handles everything, so the proof stays elementary.
- The other standard methods all require importing, explicitly or implicitly, the fact `p(s(x)) →* x`; DP is the only one that internalizes that fact using rules already in the system.
