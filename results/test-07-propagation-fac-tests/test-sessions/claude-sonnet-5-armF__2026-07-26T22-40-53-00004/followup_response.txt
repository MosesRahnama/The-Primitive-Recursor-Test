# Why LPO?

I chose the **Lexicographic Path Order** because the structure of this specific system is a textbook signature for LPO-style reasoning, and the alternative standard methods either don't apply cleanly or require more machinery than necessary. Here's the reasoning that led me there:

## 1. The system has a clear *recursive descent* pattern, not just size decrease

Look at rules 5 and 6:
```
plus(x, s(y)) -> s(plus(x, y))
plus(s(x), y) -> s(plus(x, y))
```
These don't just shrink some numeric measure — they recurse on **one argument while holding the shape of the head symbol fixed**, and the "progress" is buried inside a `s(...)` wrapper on the right. A simple **polynomial interpretation** or **Knuth–Bendix order (KBO)** can sometimes handle this, but:

- KBO requires weight/precedence choices where `s` typically must have weight ≥ 1, and it also needs equal-weight tie-breaking via precedence — this works here too, actually, but LPO is the more natural fit because...
- The **recursive-call structure is exactly what LPO is designed to detect**: LPO's core mechanism is "a term is bigger than its recursive unfolding when the head symbol stays dominant and the arguments shrink lexicographically." That is *precisely* what rules 5 and 6 do.

## 2. There's a clean, acyclic precedence hiding in the signature

The four symbols split naturally into a strict hierarchy:
```
times ≻ plus ≻ s ≻ 0
```
This isn't arbitrary — it falls out of *how the rules are written*:
- `times` only ever unfolds into `plus`-expressions (rule 2) or the constant `0` (rule 1) — so `times` must dominate `plus`.
- `plus` only ever unfolds into `s`-wrapped recursive calls — so `plus` must dominate `s`.
- `s` and `0` never get unfolded into anything by rules — they're the base constructors.

Whenever a TRS's rules show this kind of "layered unfolding" (each function symbol's RHS only calls itself or lower-precedence symbols), that's a strong signal LPO will succeed, because LPO is built exactly to exploit a fixed precedence over function symbols plus lexicographic/multiset comparison of arguments.

## 3. Subterm property handles the "base case" rules for free

Rules 1, 3, 4 (`times(x,0)->0`, `plus(x,0)->x`, `plus(0,x)->x`) are all instances of **projecting out an immediate subterm**. This is the simplest possible LPO justification (the subterm property is built into the order's definition), so no interpretation or clever argument is needed — it's automatic. This is a strong sign the order fits the problem: three of six rules are trivial base cases under LPO.

## 4. Why not other methods?

- **Polynomial/semantic interpretations**: would work too, but require guessing interpretation functions and checking inequalities over ℕ — more work, less transparent, and risks accidentally encoding extra "structural" facts about arithmetic beyond the rules (which the prompt explicitly disallows).
- **Dependency pairs**: overkill here — the system has no complex mutual recursion or nested defined symbols that would defeat a *direct* order; a simple base order (LPO) suffices without needing the DP framework's extra machinery.
- **Size-change principle / RPO variants**: RPO with multiset status would also work, but lexicographic status is the tighter, more natural fit since argument positions are used asymmetrically (only the second argument changes in most rules, so lexicographic — not multiset — comparison directly mirrors the recursion).

## 5. It stays within the requested boundary

LPO is a **purely syntactic** order defined only from the term signature (precedence + status) — it needs no external axioms, no side conditions beyond its own recursive definition, and no strengthening of the rule set. This matches the constraint of the problem: establish termination *from the rules alone*.

**In short:** I picked LPO because the rules exhibit a textbook "structural recursion with unfolding under a fixed precedence" pattern — three rules are trivial subterm eliminations, and the other three are classic recursive-call unfoldings that LPO's precedence + lexicographic comparison was specifically designed to certify, with no need for numeric interpretations or heavier frameworks like dependency pairs.
