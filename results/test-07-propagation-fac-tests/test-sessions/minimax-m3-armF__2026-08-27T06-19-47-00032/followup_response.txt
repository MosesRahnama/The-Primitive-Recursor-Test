# Why RPO was the right choice here

I chose the **Recursive Path Order (RPO)** for three concrete reasons tied to what this system actually looks like.

## 1. The system is a constructor-style definition of `times` and `plus`

The signature decomposes cleanly:

- **Constructors:** `0`, `s`
- **Defined functions:** `times`, `plus`

Every rule's left-hand side has a defined function on top, and the right-hand side is built only from constructors and **smaller recursive calls** (with the recursive argument structurally smaller). That's exactly the shape RPO is designed to handle — it's the "default" argument Dershowitz gives for why recursive definitions terminate.

## 2. There's a natural precedence that makes the proof trivial

The rules fall into two patterns:

- **Base cases** (`times(x,0) → 0`, `plus(x,0) → x`, `plus(0,x) → x`): RHS is a subterm, so the subterm clause handles them for free.
- **Recursive cases** (`plus(x, s(y)) → s(plus(x,y))`, etc.): the LHS's defined symbol is strictly above the constructor `s` on the RHS, and the recursive call is a subterm. So the **RPO status/lexicographic clause** handles them with no per-rule hand-arguing.

That clean separation is what made the proof short and per-rule mechanical.

## 3. Other standard methods are either overkill or need extra machinery

I considered the alternatives and rejected them for this problem:

- **Polynomial / matrix interpretation:** Would work, but I'd have to invent a polynomial for each symbol, solve for coefficients, and verify every rule. A lot of bookkeeping for a textbook-style system.
- **Dependency pairs + reduction pairs:** Powerful for more complex systems, but here every rule is already in "constructor" form and the call is obviously decreasing. Pulling out `(times, plus)` pairs adds notation without insight.
- **Well-founded orderings by hand (e.g., the second component `y` in `times(x, s(y))` is smaller):** True and correct — you can define a measure like $(|x|, |y|)$ and dispatch each rule. But this is essentially what RPO formalizes, and spelling it out in prose is messier and easier to get wrong than just citing the order.
- **Simplification orders other than RPO (e.g., lexicographic path order):** LPO is essentially the same here because there are no mutually recursive constructors to worry about, but RPO with a status is the more general and equally applicable choice.

## 4. RPO gives a uniform per-rule check

The problem asked me to address every rule. RPO lets me write one bullet per rule showing the same template fires, so nothing is hand-waved. That matches the constraint "stays within the boundary" — every justification is local to one rule and uses only the precedence and the structure of the rule.

## Summary

RPO was chosen because the system is exactly the kind of "constructor + defined symbol" recursive definition RPO was designed for, a single global precedence suffices, and it lets me give a short, per-rule, self-contained argument that doesn't introduce any extra symbols, axioms, or side conditions.
