A few comments on why these shapes work:

- `R_int_delta`: `delta` is transparent to both `kappa` and `mu`, so `kappa` ties and `mu` drops from `1 + mu t` to `0`.
- `R_rec_zero`: the source has `kappa = max (max (kappa b) (kappa s)) 0`, so certainly at least `kappa b`; then any number is `< that + 1` in the `delta`-successor case, but here since the third argument is `void`, you want the non-`delta` branch. Concretely, after `simp [kappa]`, the goal should reduce to showing `kappa b < max (max (kappa b) (kappa s)) 0`, which is not true in general. So this case actually needs attention: with the current definition of `kappa`, `recDelta b s void → b` does **not** obviously decrease in `kappa`, and `mu b < mu (recDelta b s void)` would be enough if `kappa` tied, but `kappa` need not tie either. So this is a likely problematic case in the current setup.
- `R_rec_succ`: this is the intended “strictly smaller recursion depth” case; the source has `... + 1`, while the target is an `app` whose `kappa` is the max of `kappa s` and `kappa (recDelta b s n)`, both bounded by the unincremented max.
- `R_eq_refl`: `kappa` does not drop to `0` unless `a` already has `kappa = 0`, so this case also does **not** fit `drop_right` uniformly. As written above, the skeleton pretends equality of `kappa`, but that won’t hold in general.
- `R_eq_diff`: this one is fine because `kappa (integrate (merge a b)) = max (kappa a) (kappa b) = kappa (eqW a b)`, while `mu` drops from `4 + ...` to `3 + ...`.

So, to be maximally useful: only **three** of the five missing cases are naturally provable with the current measure as written:

- `R_rec_succ`
- `R_eq_diff`
