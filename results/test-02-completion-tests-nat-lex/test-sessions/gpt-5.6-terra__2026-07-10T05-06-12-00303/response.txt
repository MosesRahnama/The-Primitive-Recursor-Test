The `R_rec_succ` case cannot be completed with the stated measures: `measure_decreases` is false for that rule. The other four remaining cases admit the usual “kappa drops, otherwise mu drops” skeletons.

For example, the four feasible branches can be structured as follows:

```lean
-- integrate (delta t) --> void
| _, _, Step.R_int_delta t => by
    by_cases h : kappa t = 0
    · have hmu : mu void < mu (integrate (delta t)) := by
        simp [mu]
      have hk : kappa void = kappa (integrate (delta t)) := by
        simp [kappa, h]
      exact drop_right hmu hk
    · have hpos : 0 < kappa t := Nat.pos_of_ne_zero h
      apply drop_left
      simpa [kappa] using hpos

-- recDelta b s void --> b
| _, _, Step.R_rec_zero b s => by
    by_cases h : kappa b = kappa (recDelta b s void)
    · have hmu : mu b < mu (recDelta b s void) := by
        simp [mu]
        omega
      exact drop_right hmu h
    · have hle' :
          kappa b ≤ Nat.max (Nat.max (kappa b) (kappa s)) 0 := by
        exact le_trans (Nat.le_max_left _ _) (Nat.le_max_left _ _)
      have hle : kappa b ≤ kappa (recDelta b s void) := by
        simpa [kappa] using hle'
      have hlt : kappa b < kappa (recDelta b s void) := by
        omega
      exact drop_left hlt

-- eqW a a --> void
| _, _, Step.R_eq_refl a => by
    by_cases h : kappa a = 0
    · have hmu : mu void < mu (eqW a a) := by
        simp [mu]
      have hk : kappa void = kappa (eqW a a) := by
        simp [kappa, h]
      exact drop_right hmu hk
    · have hpos : 0 < kappa a := Nat.pos_of_ne_zero h
      apply drop_left
      simpa [kappa] using hpos

-- eqW a b --> integrate (merge a b)
| _, _, Step.R_eq_diff a b => by
    have hmu : mu (integrate (merge a b)) < mu (eqW a b) := by
      simp [mu]
      omega
    have hk : kappa (integrate (merge a b)) = kappa (eqW a b) := by
      simp [kappa]
    exact drop_right hmu hk
```

However, the missing successor case has a concrete counterexample. Instantiate it with

```lean
b = void
s = void
n = delta void
```

Then the rule is

```lean
recDelta void void (delta (delta void))
  -->
app void (recDelta void void (delta void))
```

The measures are:

```text
kappa (recDelta void void (delta (delta void))) = 1
kappa (app void (recDelta void void (delta void))) = 1

mu (recDelta void void (delta (delta void))) = 3
mu (app void (recDelta void void (delta void))) = 4
```

So the target has equal `kappa` and strictly *larger* `mu`. Therefore

```text
LexOrder
  (measure (app void (recDelta void void (delta void))))
  (measure (recDelta void void (delta (delta void))))
```

does not hold.

The issue is that `delta` is transparent to both measures. In the successor rule, the outer `delta` disappears from the recursive argument, but if `n` is itself `delta`-headed then the target recursive call still receives the `+1` kappa contribution. Meanwhile the `app` constructor makes `mu` increase by one.

Thus there is no proof skeleton that can fill all five `sorry`s without changing the measure definitions or otherwise weakening/changing `measure_decreases`.
