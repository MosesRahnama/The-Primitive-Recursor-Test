No — the helper strategy is **not sound as written**.

Let

- `B := kappa b`
- `S := kappa s`
- `N := kappa n`
- `M := Nat.max (Nat.max B S) N`

Then by definition,

```lean
kappa (recDelta b s (delta n)) = M + 1
```

## 1) `kappa_rec_delta_step` is false in general

The theorem claims:

```lean
kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1
```

But `kappa (recDelta b s n)` depends on the **shape** of `n`, not just on `kappa n`:

- if `n` is **not** `delta _`, then  
  `kappa (recDelta b s n) = M`, so the equation holds;
- if `n = delta n'`, then  
  `kappa (recDelta b s n) = M + 1`, because the `recDelta` definition adds `+1` whenever its third argument is syntactically `delta _`.

So in the nested-delta case the theorem would require

```lean
M + 1 = (M + 1) + 1
```

which is impossible.

### Concrete counterexample
Take `b = void`, `s = void`, `n = delta void`.

Then:

```lean
kappa (recDelta void void (delta (delta void))) = 1
kappa (recDelta void void (delta void)) = 1
```

so the theorem asserts

```lean
1 = 1 + 1
```

i.e. `1 = 2`.

So `kappa_rec_delta_step` is false.

---

## 2) `kappa_rec_succ_drop` is also false in general

The theorem claims:

```lean
kappa (app s (recDelta b s n)) < kappa (recDelta b s (delta n))
```

Using the same counterexample `b = s = void`, `n = delta void`:

- `kappa (recDelta void void (delta void)) = 1`
- `kappa (app void (recDelta void void (delta void))) = max 0 1 = 1`
- `kappa (recDelta void void (delta (delta void))) = 1`

So it asserts:

```lean
1 < 1
```

which is false.

### General behavior
- If `n` is **not** delta-headed, then this inequality is true:
  - `kappa (recDelta b s n) = M`
  - `kappa (app s (recDelta b s n)) = max S M = M`
  - RHS is `M + 1`
  - so `M < M + 1`
- If `n = delta n'`, then:
  - `kappa (recDelta b s n) = M + 1`
  - `kappa (app s (recDelta b s n)) = max S (M + 1) = M + 1`
  - RHS is also `M + 1`
  - so you get equality, not a strict drop

So `kappa_rec_succ_drop` is only true when `n` is **not** already of the form `delta _`.

---

## 3) Why the strategy fails conceptually

The problem is that `kappa` ignores `delta` **except** in the special `recDelta ... (delta n)` branch.

So:

- `kappa (delta n) = kappa n`
- but `kappa (recDelta b s (delta n))` and `kappa (recDelta b s n)` can differ depending on whether `n` itself is syntactically `delta _`

That means the measure only detects whether the third argument of `recDelta` is delta-headed **right now**, not how many leading `delta`s remain. Hence a step like

```lean
recDelta b s (delta (delta m))  ⟶  app s (recDelta b s (delta m))
```

does **not** decrease `kappa`.

---

## 4) Extra issue for a full termination proof

Even beyond these helper theorems, `kappa` is not a strict ranking for all `Step`s:

- `merge void t -> t` preserves `kappa`
- `merge t void -> t` preserves `kappa`
- `merge t t -> t` preserves `kappa`
- `eqW a b -> integrate (merge a b)` preserves `kappa`
- `eqW a a -> void` is not strictly decreasing when `kappa a = 0`
- `integrate (delta t) -> void` is not strictly decreasing when `kappa t = 0`

So `kappa` alone cannot justify global strict descent for the whole rewrite system.

## Conclusion

The helper strategy is **unsound** as written.

- `kappa_rec_delta_step` is false.
- `kappa_rec_succ_drop` is also false.
- The failure occurs exactly when `n` is already `delta`-headed.
- More broadly, `kappa` is not a strictly decreasing measure for the full `Step` relation.
