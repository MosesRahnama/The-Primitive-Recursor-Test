The helper strategy is **unsound** as written, because the claimed theorem `kappa_rec_delta_step` is false in the given definition of `kappa`.

### Counterexample
Take `b := void`, `s := void`, `n := delta void`.  
Compute both sides:

- **Left-hand side:**  
  `kappa (recDelta void void (delta (delta void)))`  
  The third argument is a `delta`, so we use the `+1` clause:  
  `Nat.max (Nat.max (kappa void) (kappa void)) (kappa (delta void)) + 1`  
  `= Nat.max (Nat.max 0 0) 0 + 1 = 0 + 1 = 1`.

- **Right-hand side:**  
  `kappa (recDelta void void (delta void)) + 1`  
  Again the third argument is a `delta`:  
  `kappa (recDelta void void (delta void)) = Nat.max (Nat.max 0 0) (kappa void) + 1 = 0 + 1 = 1`.  
  Hence `kappa (recDelta void void n) + 1 = 1 + 1 = 2`.

We obtain `1 = 2`, which is impossible. Hence `kappa_rec_delta_step` does not hold for all `b, s, n`.

### Why it fails
The definition of `kappa` adds `1` exactly when the *immediate* third argument of `recDelta` is a `delta`. In `kappa_rec_delta_step` the argument `n` can itself be a `delta`, which makes both sides add `1`, breaking the additive relation. The lemma would only be true if `n` is guaranteed not to be a `delta`.

### Impact on the second theorem
`kappa_rec_succ_drop` depends on `kappa_rec_delta_step` (it rewrites with it). Since that rewrite is invalid, the second theorem is not reliably derived from the definition of `kappa`, and the whole termination strategy collapses.
