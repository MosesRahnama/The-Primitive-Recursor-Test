No. The helper strategy is not sound as written.

### Core issue

`kappa` treats `delta` **extensionally**:

- `kappa (delta t) = kappa t`

but `kappa` treats `recDelta` **syntactically** in its third argument:

- `kappa (recDelta b s (.delta n)) = ... + 1`
- `kappa (recDelta b s n) = ...` otherwise

So whether you get the extra `+1` depends on the **shape** of the third argument, not just its `kappa` value.

That breaks the intended lemma.

---

## 1) `kappa_rec_delta_step` is false

The theorem claims:

```lean
kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1
```

Let

- `Kb = kappa b`
- `Ks = kappa s`

and consider two cases.

### Case A: `n` is **not** of the form `delta m`

Then this works:

- `kappa (recDelta b s (delta n)) = max (max Kb Ks) (kappa n) + 1`
- `kappa (recDelta b s n) = max (max Kb Ks) (kappa n)`

so indeed LHS = RHS.

### Case B: `n = delta m`

Then:

- `kappa n = kappa (delta m) = kappa m`
- `kappa (recDelta b s (delta n)) = kappa (recDelta b s (delta (delta m))) = max (max Kb Ks) (kappa m) + 1`
- but also `kappa (recDelta b s n) = kappa (recDelta b s (delta m)) = max (max Kb Ks) (kappa m) + 1`

So the claimed RHS becomes:

- `kappa (recDelta b s n) + 1 = max (max Kb Ks) (kappa m) + 2`

while the LHS is only

- `max (max Kb Ks) (kappa m) + 1`

So the theorem fails.

### Concrete counterexample

Take `b = void`, `s = void`, `n = delta void`.

Then:

- `kappa void = 0`
- `kappa (delta void) = 0`

Hence:

- `kappa (recDelta void void (delta (delta void))) = 0 + 1 = 1`
- `kappa (recDelta void void (delta void)) = 0 + 1 = 1`

So the theorem would assert:

- `1 = 1 + 1`

i.e. `1 = 2`, impossible.

---

## 2) `kappa_rec_succ_drop` is also false

The theorem claims:

```lean
kappa (app s (recDelta b s n)) < kappa (recDelta b s (delta n))
```

Again, if `n` is not a `delta`, it does hold.

But if `n = delta m`, it fails.

Let

- `M = max (max (kappa b) (kappa s)) (kappa m)`

Then:

- `kappa (recDelta b s (delta (delta m))) = M + 1`
- `kappa (recDelta b s (delta m)) = M + 1`

Therefore:

- `kappa (app s (recDelta b s (delta m))) = max (kappa s) (M + 1) = M + 1`

since `kappa s ≤ M`.

So both sides are equal:

- `kappa (app s (recDelta b s (delta m))) = kappa (recDelta b s (delta (delta m)))`

not strictly less.

### Same concrete counterexample

Take `b = void`, `s = void`, `n = delta void`.

Then:

- `kappa (recDelta void void (delta void)) = 1`
- `kappa (app void (recDelta void void (delta void))) = max 0 1 = 1`
- `kappa (recDelta void void (delta (delta void))) = 1`

So the theorem would assert:

- `1 < 1`

false.

---

## 3) Why the proof sketch is misleading

The second proof starts with:

```lean
rw [kappa_rec_delta_step]
```

If you *assume* the first theorem, the new goal becomes something like

```lean
kappa (app s (recDelta b s n)) < kappa (recDelta b s n) + 1
```

which is plausible.

But that rewrite is invalid because `kappa_rec_delta_step` itself is false.

So the strategy “prove theorem 1, rewrite, then finish theorem 2” is unsound.

---

## 4) Broader termination note

Even beyond these two lemmas, `kappa` is not a strict decrease for many `Step` rules:

- `merge void t -> t` preserves `kappa`
- `merge t void -> t` preserves `kappa`
- `merge t t -> t` preserves `kappa`
- `eqW a b -> integrate (merge a b)` preserves `kappa`

So `kappa` alone cannot serve as a global strictly decreasing termination measure for `Step`.

That does **not** mean the rewrite system is nonterminating; it only means this particular helper measure/lemma strategy does not establish termination.

---

## Conclusion

The helper strategy is **unsound as written**.

- `kappa_rec_delta_step` is false in general.
- `kappa_rec_succ_drop` is also false in general.
- A simple counterexample is `b = void`, `s = void`, `n = delta void`.

The root cause is the mismatch between:

- `delta` being invisible to `kappa`, and
- `recDelta` giving a special `+1` based on whether its argument is **syntactically** a `delta`.
