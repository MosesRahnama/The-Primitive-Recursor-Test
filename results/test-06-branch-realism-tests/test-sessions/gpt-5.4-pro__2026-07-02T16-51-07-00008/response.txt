No — the helper strategy is **not sound as written**.

The core problem is that both helper theorems are **false** for nested `delta`s.

## Why `kappa_rec_delta_step` fails

Let

\[
M := \max(\max(\kappa b,\kappa s),\kappa n).
\]

From the definition,

\[
\kappa(\mathrm{recDelta}\ b\ s\ (\delta n)) = M + 1.
\]

But `κ (recDelta b s n)` depends on the **shape** of `n`:

- if `n` is **not** of the form `delta _`, then  
  \[
  \kappa(\mathrm{recDelta}\ b\ s\ n)=M,
  \]
  so the theorem would be true;

- if `n = delta m`, then  
  \[
  \kappa(\mathrm{recDelta}\ b\ s\ n)
  = \kappa(\mathrm{recDelta}\ b\ s\ (\delta m))
  = \max(\max(\kappa b,\kappa s),\kappa m)+1.
  \]
  Since \(\kappa(\delta m)=\kappa m\), this is exactly \(M+1\).

So in that case the theorem claims

\[
M+1 = (M+1)+1,
\]

which is impossible.

### Concrete counterexample
Take:

- `b = void`
- `s = void`
- `n = delta void`

Then:

- \(\kappa(void)=0\)
- \(\kappa(\mathrm{recDelta}\ void\ void\ (\delta(\delta void))) = 1\)
- \(\kappa(\mathrm{recDelta}\ void\ void\ (\delta void)) = 1\)

So `kappa_rec_delta_step` becomes

\[
1 = 1 + 1,
\]

i.e.

\[
1 = 2,
\]

false.

---

## Why `kappa_rec_succ_drop` fails

First note that for **all** `b s n`,

\[
\kappa(\mathrm{app}\ s\ (\mathrm{recDelta}\ b\ s\ n))
= \kappa(\mathrm{recDelta}\ b\ s\ n),
\]

because `κ (recDelta b s n)` is always at least `κ s`, so the `max` in `kappa_app` just returns the recursive part.

Thus the second theorem is really asking for

\[
\kappa(\mathrm{recDelta}\ b\ s\ n)
<
\kappa(\mathrm{recDelta}\ b\ s\ (\delta n)).
\]

That is true when `n` is not `delta _`, but it fails when `n = delta m`, because then both sides are equal.

### Same concrete counterexample
Again let `b = void`, `s = void`, `n = delta void`.

Then:

- \(\kappa(\mathrm{recDelta}\ void\ void\ (\delta void)) = 1\)
- \(\kappa(\mathrm{app}\ void\ (\mathrm{recDelta}\ void\ void\ (\delta void))) = 1\)
- \(\kappa(\mathrm{recDelta}\ void\ void\ (\delta(\delta void))) = 1\)

So `kappa_rec_succ_drop` becomes

\[
1 < 1,
\]

false.

---

## Intuition for the failure

`kappa` **forgets `delta` layers** almost everywhere:

- `kappa (delta t) = kappa t`

but it gives a `+1` only when the third argument of `recDelta` is **syntactically** a `delta`.

So for
```lean
recDelta b s (delta (delta m))
```
the outer `delta` contributes the `+1`, but after one `R_rec_succ` step you get
```lean
app s (recDelta b s (delta m))
```
and the inner `recDelta ... (delta m)` still has the same `+1`. Hence no strict drop.

---

## Broader issue: `kappa` is not a strict termination measure for `Step`

Even beyond these two lemmas, several rewrite rules preserve `kappa` exactly:

- `merge void t → t`:
  \[
  \kappa(\mathrm{merge}\ void\ t)=\max(0,\kappa t)=\kappa t
  \]
- `merge t void → t`: same
- `merge t t → t`:
  \[
  \max(\kappa t,\kappa t)=\kappa t
  \]
- `eqW a b → integrate (merge a b)`:
  \[
  \kappa(\mathrm{eqW}\ a\ b)=\max(\kappa a,\kappa b)
  \]
  and
  \[
  \kappa(\mathrm{integrate}(\mathrm{merge}\ a\ b))
  = \kappa(\mathrm{merge}\ a\ b)
  = \max(\kappa a,\kappa b).
  \]

So a proof of termination based on “every `Step` strictly lowers `kappa`” cannot work with this `kappa`.

---

## Conclusion

The helper strategy is **unsound as written**:

- `kappa_rec_delta_step` is false in general.
- `kappa_rec_succ_drop` is also false in general.
- More broadly, `kappa` is not a strict descent measure for several rewrite rules.

This does **not** mean the rewrite system is nonterminating; it means only that this particular `kappa`-based strict-decrease argument does not go through in its current form.
