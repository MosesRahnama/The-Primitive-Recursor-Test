**Conclusion:** The helper strategy is **unsound as written**. Both lemmas are false in general, because the measure `kappa` fails to distinguish a single `delta` from a nested chain of `delta`s. Consequently the purported termination argument for the `R_rec_succ` rule collapses when the predecessor `n` is itself a `delta`.

---

### Where the lemmas break

Recall the definition of `kappa` on `recDelta`:

```lean
| .recDelta b s (.delta n) => Nat.max (Nat.max (kappa b) (kappa s)) (kappa n) + 1
| .recDelta b s n          => Nat.max (Nat.max (kappa b) (kappa s)) (kappa n)
```

The `+1` is added **only when the third argument is syntactically an immediate `delta`**. It does **not** recursively count how many `delta` constructors are nested inside. Thus `kappa` behaves like a boolean flag on that position.

Take the concrete counter‑example:

```lean
b := void
s := void
n := delta void
```

Since `kappa void = 0` and `kappa (delta t) = kappa t`, we have:

* `kappa n = kappa (delta void) = 0`.

#### 1. `kappa_rec_delta_step` fails

* **LHS:**  
  `kappa (recDelta void void (delta (delta void)))`  
  `= Nat.max (Nat.max 0 0) (kappa void) + 1`  
  `= 0 + 1 = 1`.

* **RHS:**  
  `kappa (recDelta void void (delta void)) + 1`  
  `= (Nat.max (Nat.max 0 0) (kappa void) + 1) + 1`  
  `= (0 + 1) + 1 = 2`.

So the equation `1 = 2` is false. The lemma does **not** hold universally.

#### 2. `kappa_rec_succ_drop` fails

* **LHS:**  
  `kappa (app void (recDelta void void (delta void)))`  
  `= Nat.max (kappa void) (kappa (recDelta void void (delta void)))`  
  `= Nat.max 0 1 = 1`.

* **RHS:**  
  `kappa (recDelta void void (delta (delta void))) = 1` (computed above).

So the strict inequality `1 < 1` is false.

---

### Why the measure cannot work

Consider the rewrite step

```lean
recDelta b s (delta n)  -->  app s (recDelta b s n)
```

and inspect `kappa` on both sides for the two possible shapes of `n`.

**Case 1: `n` is *not* a `delta`.**  
Let `M := Nat.max (Nat.max (kappa b) (kappa s)) (kappa n)`.

* LHS: `kappa (recDelta b s (delta n)) = M + 1`.
* RHS: `kappa (app s (recDelta b s n)) = Nat.max (kappa s) M = M`, because `M ≥ kappa s`.  
  Here `M < M + 1`, so the measure does decrease.

**Case 2: `n` *is* a `delta`, say `n = delta n'`.**  
Let `M' := Nat.max (Nat.max (kappa b) (kappa s)) (kappa n')`.

* LHS: `kappa (recDelta b s (delta (delta n'))) = M' + 1`.
* RHS: `kappa (recDelta b s n) = kappa (recDelta b s (delta n')) = M' + 1`.  
  Hence `kappa (app s (recDelta b s n)) = Nat.max (kappa s) (M' + 1) = M' + 1` (since `M' + 1 > kappa s`).

So in this case **both sides have exactly the same `kappa`**; the measure is unchanged by the rewrite. Because the step relation can be applied to terms like `recDelta b s (delta (delta void))`, where the predecessor is already a `delta`, `kappa` never decreases. It is therefore impossible to prove well‑foundedness of `R_rec_succ` using `kappa` as a decreasing measure.

---

### Summary

* `kappa_rec_delta_step` is false when `n` is a `delta` (e.g. `n = delta void`).
* `kappa_rec_succ_drop` is false in the same situation.
* The root cause is that `kappa` treats the third argument of `recDelta` as a flat “is‑it‑a‑delta?” test rather than a nested depth count. As a result, the `R_rec_succ` step does **not** strictly decrease `kappa` whenever the predecessor already contains a `delta`.

Therefore the proposed helper strategy—proving termination of `recDelta` rewriting via these two lemmas—is **unsound as written**. A valid termination argument would require a measure that actually counts the nesting depth of `delta` constructors (or another lexicographic ordering), not merely tests the top‑level shape.
