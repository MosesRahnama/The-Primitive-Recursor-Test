**Assessment: the helper strategy is unsound as written.**

Both theorems are false for arbitrary traces because the definition of `kappa` treats a `delta` in the third argument of `recDelta` specially (adding +1), and this interacts badly with nested `delta`s.  The failure already appears for the simple numeral `n = delta void`.

---

### 1.  `kappa_rec_delta_step` is false

**Counterexample.**  Take `b = void`, `s = void`, `n = delta void`.

First compute the needed base values:
* `kappa void = 0`
* `kappa (delta void) = kappa void = 0`
* `kappa (delta (delta void)) = kappa (delta void) = 0`

**Left‑hand side**
```lean
kappa (recDelta void void (delta (delta void)))
```
matches the `.recDelta b s (.delta n)` branch of `kappa`, so it equals
```
Nat.max (Nat.max (kappa void) (kappa void)) (kappa (delta void)) + 1
= Nat.max (Nat.max 0 0) 0 + 1 = 1
```

**Right‑hand side**
```lean
kappa (recDelta void void (delta void)) + 1
```
Here `recDelta void void (delta void)` also matches the `.delta` branch:
```
(Nat.max (Nat.max (kappa void) (kappa void)) (kappa void) + 1) + 1
= (Nat.max (Nat.max 0 0) 0 + 1) + 1 = 2
```

So the claimed equality is `1 = 2`, which is false.

**Why it fails in general.**  
If `n = delta t` for some `t`, then both `recDelta b s (delta n)` and `recDelta b s n` fall into the `.recDelta b s (.delta _)` pattern of `kappa`.  Writing
```
M = Nat.max (Nat.max (kappa b) (kappa s)) (kappa t)
```
we have
* `kappa (recDelta b s (delta (delta t))) = M + 1`
* `kappa (recDelta b s (delta t))     = M + 1`

Hence `kappa_rec_delta_step` would require `M + 1 = (M + 1) + 1`, which never holds.  
The theorem is only true when `n` is **not** itself a `delta`.

---

### 2.  `kappa_rec_succ_drop` is false

Using the same counterexample `b = void`, `s = void`, `n = delta void`:

**Left‑hand side**
```lean
kappa (app void (recDelta void void (delta void)))
= Nat.max (kappa void) (kappa (recDelta void void (delta void)))
= Nat.max 0 1 = 1
```

**Right‑hand side**
```lean
kappa (recDelta void void (delta (delta void))) = 1   -- calculated above
```

The theorem claims `1 < 1`, which is false.

**Why it fails in general.**  
Again let `n = delta t` and let `M` be as above. Then:
* `kappa (recDelta b s (delta n)) = kappa (recDelta b s (delta (delta t))) = M + 1`.
* The inner term `recDelta b s n = recDelta b s (delta t)` also has measure `M + 1`.
* Therefore
  ```
  kappa (app s (recDelta b s n))
  = Nat.max (kappa s) (M + 1)
  = M + 1                (since M ≥ kappa s)
  ```

So for any `n` of the form `delta t`,
```
kappa (app s (recDelta b s n)) = kappa (recDelta b s (delta n))
```
and the strict inequality required by `kappa_rec_succ_drop` collapses to an equality.  
It only strictly decreases when `n` is *not* a `delta` (e.g. `n = void`).

---

### Conclusion

The measure `kappa` does **not** strictly decrease under the rewrite rule
```
R_rec_succ : recDelta b s (delta n)  →  app s (recDelta b s n)
```
whenever `n` is itself a `delta` term.  In particular, already for the numeral `n = delta void` (representing “1”) the redex and the contractum have the same `kappa` value.  Consequently:

* `kappa_rec_delta_step` is an over‑generalisation: it is off‑by‑one when `n` is a `delta`.
* `kappa_rec_succ_drop` is false for the same family of terms.

Because the two helper theorems are false as universally quantified statements, the termination argument built from them is **unsound**.  A correct measure would need to account for the *entire* stack of `delta` constructors in the third argument (or use a different recursion scheme) so that each application of `R_rec_succ` provably decreases it.
