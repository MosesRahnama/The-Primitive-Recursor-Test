**Conclusion: the helper strategy is unsound as written.**  
Both auxiliary theorems are false in general. In particular, when the variable `n` is itself headed by a `delta`, the claimed strict decrease collapses to an equality, and the intermediate equality claims a false increment. Below are the detailed calculations.

---

### 1.  Where `kappa_rec_delta_step` fails

The theorem claims

```
kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1     for all b, s, n.
```

Unfold the definition of `kappa` on `recDelta`.

*Left-hand side.*  
Because the third argument is syntactically `delta n`, the first `recDelta`-clause of `kappa` applies:

```
kappa (recDelta b s (delta n))
= Nat.max (Nat.max (kappa b) (kappa s)) (kappa n) + 1.          (1)
```

*Right-hand side.*  
Here `n` is an arbitrary `Trace`. If `n` happens to be of the form `delta m`, then the same clause fires again:

```
kappa (recDelta b s n)
= kappa (recDelta b s (delta m))
= Nat.max (Nat.max (kappa b) (kappa s)) (kappa m) + 1.          (2)
```

Now set `n := delta m`.  
Using (1) with `n` instantiated to `delta m`:

```
LHS = Nat.max (Nat.max (kappa b) (kappa s)) (kappa (delta m)) + 1
    = Nat.max (Nat.max (kappa b) (kappa s)) (kappa m) + 1
    =: X + 1.
```

Using (2):

```
RHS = kappa (recDelta b s (delta m)) + 1
    = (Nat.max (Nat.max (kappa b) (kappa s)) (kappa m) + 1) + 1
    = (X + 1) + 1 = X + 2.
```

Thus for every `b, s, m` we get `X + 1 = X + 2`, which is impossible.

**Concrete counterexample.**  
Take `b = void`, `s = void`, `n = delta void`.

* `kappa void = 0`.
* `kappa (delta void) = 0`.

Then

```
kappa (recDelta void void (delta (delta void)))
= max (max 0 0) 0 + 1 = 1.

kappa (recDelta void void (delta void)) + 1
= (max (max 0 0) 0 + 1) + 1 = 2.
```

The claimed equation `1 = 2` is false.

---

### 2.  Where `kappa_rec_succ_drop` fails

The theorem claims

```
kappa (app s (recDelta b s n)) < kappa (recDelta b s (delta n))   for all b, s, n.
```

Again consider the case `n = delta m`.

*Left-hand side.*

```
kappa (app s (recDelta b s (delta m)))
= Nat.max (kappa s) (kappa (recDelta b s (delta m)))
= Nat.max (kappa s) (Nat.max (Nat.max (kappa b) (kappa s)) (kappa m) + 1)
= Nat.max (kappa s) (X + 1),
```

where `X = Nat.max (Nat.max (kappa b) (kappa s)) (kappa m)`.

Because `X ≥ Nat.max (kappa b) (kappa s) ≥ kappa s`, we have `X + 1 > kappa s`, so the `max` resolves to `X + 1`. Hence

```
LHS = X + 1.
```

*Right-hand side.*

```
kappa (recDelta b s (delta (delta m)))
= Nat.max (Nat.max (kappa b) (kappa s)) (kappa (delta m)) + 1
= Nat.max (Nat.max (kappa b) (kappa s)) (kappa m) + 1
= X + 1.
```

So for `n = delta m` we obtain

```
LHS = X + 1  and  RHS = X + 1,
```

which contradicts the strict inequality `LHS < RHS`.

**Concrete counterexample.**  
Reuse `b = void`, `s = void`, `n = delta void`.

```
kappa (app void (recDelta void void (delta void)))
= max (kappa void) (kappa (recDelta void void (delta void)))
= max 0 (max (max 0 0) 0 + 1)
= max 0 1 = 1.

kappa (recDelta void void (delta (delta void))) = 1   (as computed above).
```

Thus the claimed inequality `1 < 1` is false.

---

### 3.  Why the strategy cannot be rescued

The proof of `kappa_rec_succ_drop` begins with

```lean
rw [kappa_rec_delta_step]
```

which would rewrite the right-hand side to `kappa (recDelta b s n) + 1`. Even if this rewrite were valid, the remaining step would be to show

```
Nat.max (kappa s) (kappa (recDelta b s n)) < kappa (recDelta b s n) + 1.
```

Since `kappa (recDelta b s n) ≥ kappa s` for every `b, s, n` (the definition of `kappa` on `recDelta` is always at least `Nat.max (kappa b) (kappa s)`), the left-hand side equals `kappa (recDelta b s n)`, and the strict inequality would indeed follow. So the *remaining* reasoning is correct.

The fatal flaw is that `kappa_rec_delta_step` itself is not a true unconditional equation: wrapping an *additional* `delta` around `n` does **not** increase `kappa` by 1 when `n` is already a `delta`. The `+1` in the definition of `kappa` is tied to the *outermost* shape of the third argument; it does not accumulate through nested `delta`s. Consequently, on the rewrite rule

```
R_rec_succ : recDelta b s (delta n)  -->  app s (recDelta b s n)
```

the measure `kappa` stays **exactly the same** whenever `n` is of the form `delta m`. It never increases, but it also does not strictly decrease. A termination argument based on a strictly decreasing natural measure therefore cannot go through with this definition of `kappa`.

---

**Verdict:** The helper strategy is **unsound**. Both lemmas are falsified by taking `n` to be a `delta` (e.g., `n = delta void`), and the proposed measure `kappa` fails to establish strict decrease for the `R_rec_succ` rewrite step.
