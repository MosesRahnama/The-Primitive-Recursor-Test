The helper strategy is not sound. To see this, instantiate `b = void`, `s = void`, and `n = delta void` (all valid by the `Trace` constructors). Then `kappa void = 0` and `kappa (delta void) = 0` (by the `kappa` definition and its `kappa_void`/`kappa_delta` lemmas).

This yields:
- `kappa (recDelta void void (delta void)) = Nat.max (Nat.max 0 0) 0 + 1 = 1` (by the first `recDelta` case in `kappa`, since the third argument matches the `.delta _` pattern).
- `kappa (recDelta void void (delta (delta void))) = Nat.max (Nat.max 0 0) 0 + 1 = 1` (again by the first `recDelta` case in `kappa`).
- `kappa (app void (recDelta void void (delta void))) = Nat.max 0 1 = 1` (by the `app` case in `kappa`).

Thus `kappa_rec_delta_step` fails because `1 ≠ 1 + 1`. Likewise `kappa_rec_succ_drop` fails because `1 < 1` is false (and the `rw [kappa_rec_delta_step]` does not help, as the preceding lemma is already invalid). These counterexamples hold for arbitrary `b` and `s` (the `Nat.max` expressions are unaffected).

The `Step` relation can produce this case (via `R_rec_succ` with the chosen `n`), so the intended termination argument does not go through.
