The helper strategy is **not sound as written**. Both helper theorems are false when `n` itself begins with `delta`.

Let

```lean
b := void
s := void
n := delta void
```

All component `kappa` values are `0`.

For the first helper:

```lean
kappa (recDelta void void (delta (delta void)))
```

matches the special `.delta` equation, so it is

```text
max (max 0 0) (kappa (delta void)) + 1 = 1.
```

But

```text
kappa (recDelta void void (delta void)) + 1
= (max (max 0 0) (kappa void) + 1) + 1
= 2.
```

Thus `kappa_rec_delta_step` claims `1 = 2`.

The second helper fails on the same instance:

```text
kappa (app void (recDelta void void (delta void)))
= max 0 1
= 1,
```

while

```text
kappa (recDelta void void (delta (delta void))) = 1.
```

Hence `kappa_rec_succ_drop` claims `1 < 1`.

The problem is the overlapping equations in `kappa`:

```lean
| .recDelta b s (.delta n) => ... + 1
| .recDelta b s n          => ...
```

When `n` itself is a `delta`, `kappa (recDelta b s n)` also uses the first branch and already includes `+ 1`. Meanwhile, wrapping `n` in another `delta` does not increase `kappa n`, since `kappa (delta n) = kappa n`. Consequently, the rewrite step

```lean
recDelta b s (delta n) ↦ app s (recDelta b s n)
```

does not strictly decrease `kappa` for nested `delta` arguments. Both stated helper theorems therefore cannot be proved from these definitions.
