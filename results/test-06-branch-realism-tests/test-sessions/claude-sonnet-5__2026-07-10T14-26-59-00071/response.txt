## Summary

Both helper theorems are **false as stated**, so no valid proof of either can exist — the `sorry`s cannot be legitimately discharged. The problem is a genuine flaw in `kappa`: the `+1` in the `recDelta b s (.delta n)` clause is only ever charged for the *outermost* `delta` layer of the third argument, so peeling one `delta` off a term whose remaining argument is *itself* `delta`-headed does not actually decrease `kappa` by one — it doesn't decrease it at all.

## Counterexample computation

Take `b := void`, `s := void`, `n := delta void`.

**`kappa_rec_delta_step`** claims
`kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1`.

- `kappa (recDelta void void n)` with `n = delta void`: the third argument `delta void` matches the special pattern `.delta n'` (`n' = void`), so
`kappa = max(max(0,0), kappa void) + 1 = 0 + 1 = 1`.
- `kappa (recDelta void void (delta n))` with `delta n = delta (delta void)`: this matches `.delta n'` with `n' = delta void`, so
`kappa = max(max(0,0), kappa (delta void)) + 1 = max(0, 0) + 1 = 1` (using `kappa (delta void) = kappa void = 0`).

So LHS `= 1` but RHS `= kappa(recDelta b s n) + 1 = 1 + 1 = 2`. **1 ≠ 2**, contradiction.

In general, for `n = delta m`:
- `kappa (recDelta b s n) = max(max(kb,ks), kappa m) + 1`
- `kappa (recDelta b s (delta n)) = max(max(kb,ks), kappa m) + 1` (since `kappa (delta m) = kappa m`)

so the two sides differ by exactly 1 whenever `n` is `delta`-headed, **independent of `b, s, m`**. This is not an edge case; it's a systematic bug.

**`kappa_rec_succ_drop`** claims
`kappa (app s (recDelta b s n)) < kappa (recDelta b s (delta n))`.

Using the same instantiation (`b = s = void`, `n = delta void`):

- `kappa (recDelta void void (delta void)) = 1` (computed above).
- `kappa (app void (recDelta void void (delta void))) = max(kappa void, 1) = 1`.
- `kappa (recDelta void void (delta (delta void))) = 1` (computed above).

So the claim reduces to `1 < 1`, which is **false**.

More generally, splitting on whether `n` is `delta`-headed:

- If `n` is **not** `delta`-headed: `kappa(recDelta b s n) = max(max(kb,ks), kappa n)`, giving
`kappa(app s (recDelta b s n)) = max(max(kb,ks), kappa n) = kappa(recDelta b s (delta n)) - 1`, so strict `<` holds.
- If `n` **is** `delta`-headed (`n = delta m`): `kappa(recDelta b s n) = max(max(kb,ks), kappa n) + 1`, giving
`kappa(app s (recDelta b s n)) = max(max(kb,ks), kappa n) + 1 = kappa(recDelta b s (delta n))` — **equality**, not strict decrease.

## Conclusion

The strategy is **unsound**. `kappa_rec_delta_step` is false whenever `n` is itself `delta`-headed (off by exactly 1 in every such instance, as shown above), and consequently `kappa_rec_succ_drop` — which is precisely the lemma needed to show `kappa` strictly decreases across the `R_rec_succ` rewrite `recDelta b s (delta n) ⇝ app s (recDelta b s n)` — fails exactly on inputs like `n = delta n'` (i.e., whenever the rule is applied to a term of shape `recDelta b s (delta (delta n'))`), where `kappa` only stays equal rather than strictly decreasing. Since this is a legitimate, non-degenerate instance of the rewrite rule (not an unreachable case), `kappa` as defined cannot support a termination argument via strict decrease on this rule, and the two theorems as stated are mathematically false rather than merely hard to prove.
