The helper strategy is **unsound** because the key lemma `kappa_rec_delta_step` is false as stated.

The definition of `kappa` distinguishes two cases for `recDelta`:

* `kappa (recDelta b s (delta n)) = max(max(kappa b, kappa s), kappa n) + 1`
* `kappa (recDelta b s n) = max(max(kappa b, kappa s), kappa n)` when `n` is **not** a `delta`.

The lemma asserts that for *every* `n`,
\[
\kappa(\texttt{recDelta } b\; s\; (\texttt{delta } n)) = \kappa(\texttt{recDelta } b\; s\; n) + 1.
\]
This equality fails precisely when `n` itself is a `delta`. In that case the right‑hand side matches the first pattern as well, leading to an extra `+1` that is not matched on the left.

**Counterexample**  
Take `b = s = void` and `n = delta void`. Compute both sides:

- Left‑hand side:  
  \(\kappa(\texttt{recDelta void void (delta (delta void))}) = \max(\max(0,0),\, \kappa(\texttt{delta void})) + 1 = \max(0,0) + 1 = 1\).

- Right‑hand side:  
  \(\kappa(\texttt{recDelta void void (delta void)}) + 1\)  
  \(= \bigl(\max(\max(0,0),\, \kappa(\texttt{void})) + 1\bigr) + 1 = (0 + 1) + 1 = 2\).

Thus \(1 = 2\), contradiction.  

Because the proof of `kappa_rec_succ_drop` relies on rewriting with `kappa_rec_delta_step`, the entire helper strategy collapses. No consistent termination argument can be built on these lemmas as written.
