The helper strategy is not sound as written.

The issue is with the first helper theorem:

```lean
theorem kappa_rec_delta_step (b s n : Trace) :
  kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1 := by
```

This is false in general because `kappa` was defined by cases on the third argument of `recDelta`:

- if the third argument is literally of the form `delta n`, then
  ```lean
  kappa (recDelta b s (delta n))
    = max (max (kappa b) (kappa s)) (kappa n) + 1
  ```
- otherwise
  ```lean
  kappa (recDelta b s n)
    = max (max (kappa b) (kappa s)) (kappa n)
  ```

But when `n` itself is of the form `delta m`, the term `recDelta b s n` also matches the special `.delta` case, so it already carries a `+1`. In that case the claimed equality becomes wrong.

Let
```lean
M := Nat.max (Nat.max (kappa b) (kappa s)) (kappa n)
```
Then the left-hand side is always `M + 1`, since `kappa (delta n) = kappa n`.

However, the right-hand side depends on the shape of `n`:

- if `n` is not syntactically `delta _`, then
  ```lean
  kappa (recDelta b s n) = M
  ```
  so the equality holds.

- if `n = delta m`, then
  ```lean
  kappa (recDelta b s n) = kappa (recDelta b s (delta m)) = M + 1
  ```
  and thus
  ```lean
  kappa (recDelta b s n) + 1 = M + 2
  ```
  while
  ```lean
  kappa (recDelta b s (delta n)) = M + 1.
  ```
  So it would assert `M + 1 = M + 2`, impossible.

Concrete counterexample:
- take `b = void`, `s = void`, `n = delta void`.

Then:
- `kappa b = 0`
- `kappa s = 0`
- `kappa n = kappa (delta void) = 0`

Hence
```lean
kappa (recDelta void void (delta (delta void))) = 0 + 1 = 1
```
but
```lean
kappa (recDelta void void (delta void)) = 1
```
so
```lean
kappa (recDelta void void (delta void)) + 1 = 2.
```
Therefore the theorem would claim `1 = 2`.

So the first helper theorem is false.

Because the second helper theorem starts with

```lean
rw [kappa_rec_delta_step]
```

its proof strategy depends on the first theorem, so as written it is unsound too.

That said, the second statement itself is actually true:

```lean
theorem kappa_rec_succ_drop (b s n : Trace) :
  kappa (app s (recDelta b s n)) < kappa (recDelta b s (delta n))
```

To see this, write
```lean
A := kappa b
S := kappa s
N := kappa n
M := Nat.max (Nat.max A S) N
```

Then
```lean
kappa (recDelta b s (delta n)) = M + 1.
```

Now
```lean
kappa (app s (recDelta b s n)) = Nat.max S (kappa (recDelta b s n)).
```

There are two cases.

1. `n` is not of the form `delta _`.

Then
```lean
kappa (recDelta b s n) = M,
```
so
```lean
kappa (app s (recDelta b s n)) = Nat.max S M = M
```
since `S ≤ M`. Hence
```lean
M < M + 1.
```

2. `n = delta m`.

Then
```lean
kappa (recDelta b s n) = M + 1
```
where here `M = max (max A S) (kappa m)`. So
```lean
kappa (app s (recDelta b s n)) = Nat.max S (M + 1) = M + 1
```
because `S ≤ M + 1`.

But now
```lean
kappa (recDelta b s (delta n)) = kappa (recDelta b s (delta (delta m))) = M + 1,
```
not bigger. So in this case the desired strict inequality fails as well.

Concrete counterexample again with `b = void`, `s = void`, `n = delta void`:
- `kappa (app void (recDelta void void (delta void))) = max 0 1 = 1`
- `kappa (recDelta void void (delta (delta void))) = 1`

So the theorem would claim `1 < 1`, false.

Conclusion:

- `kappa_rec_delta_step` is false.
- `kappa_rec_succ_drop` is also false.
- Therefore the helper strategy is not sound as written.

The underlying problem is that `kappa` distinguishes whether the third argument of `recDelta` is syntactically a `delta _`, so adding one outer `delta` does not uniformly increase `kappa` by 1 when the argument already had that shape.
