The two helper lemmas are false as stated. The intended termination argument therefore fails.

### Counterexample for `kappa_rec_delta_step`
Take `b := void`, `s := void`, `n := delta void`.  
Compute:
- `kappa (recDelta void void (delta (delta void)))`  
  The third argument is `delta (delta void)`, which matches the first case:  
  `kappa = max(max(kappa void, kappa void), kappa(delta void)) + 1`  
  `= max(max(0,0), 0) + 1 = 1`.
- `kappa (recDelta void void (delta void)) + 1`  
  `kappa(recDelta void void (delta void))` also matches the first case:  
  `kappa = max(max(0,0), kappa void) + 1 = 1`.  
  Thus `1 + 1 = 2`.  
So `1 ≠ 2`, contradicting the claimed equality.

### Counterexample for `kappa_rec_succ_drop`
Using the same `b, s, n`:  
- Left side: `kappa (app void (recDelta void void (delta void)))`  
  `= max(kappa void, kappa(recDelta void void (delta void)))`  
  `= max(0,1) = 1`.
- Right side: `kappa (recDelta void void (delta (delta void))) = 1`.  
  Hence `1 < 1` is false.

### Why the lemmas fail
- `kappa_rec_delta_step` assumes that `kappa(recDelta b s n)` is computed by the catch‑all case, but when `n` itself is a `delta`, it matches the first case and already includes the `+1`. The equation then double‑counts the increment.
- `kappa_rec_succ_drop` relies on the previous lemma, but even without it, when `n` is a `delta` the two sides become equal, not strictly decreasing. The measure `kappa` does not strictly decrease for the rule `R_rec_succ` when the third argument of `recDelta` is already a `delta`.

Thus the helper strategy is unsound as written.
