### Why `kappa_rec_delta_step` fails

The equation lemmas for `kappa` on `recDelta` are generated by matching on the *head constructor* of the third argument:

* `kappa (recDelta b s (delta n)) = max(max(kappa b, kappa s), kappa n) + 1`
* `kappa (recDelta b s n) = max(max(kappa b, kappa s), kappa n)` **only when `n` is not of the form `delta _`**.

So the `+1` is added **only for the outermost `delta`-wrapping**, and it is *not* a measure of how deeply `n` is nested in further `delta`s, because `kappa (delta t) = kappa t` collapses all further nesting to the same value.

The claimed lemma

```
kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1
```

is quantified over **all** `n`, including `n` itself of the form `delta m`. Take a concrete counterexample:

`b = s = void`, `n = delta void`.

* LHS: `recDelta void void (delta (delta void))` matches the `delta`-headed clause with inner term `delta void`:
  `kappa = max(max(0,0), kappa(delta void)) + 1 = max(0,0) + 1 = 1`.

* RHS: `kappa (recDelta void void (delta void)) + 1`. Here `recDelta void void (delta void)` again matches the `delta`-headed clause:
  `kappa = max(max(0,0), kappa void) + 1 = 0 + 1 = 1`, so RHS `= 1 + 1 = 2`.

So LHS `= 1` but RHS `= 2`. The two sides disagree, so `kappa_rec_delta_step` is **false** in general (it only holds when `n` is not itself `delta`-headed). Since it is false, no legal Lean proof of it exists; the `sorry` cannot be soundly discharged.

### Why `kappa_rec_succ_drop` fails independently

Even ignoring the broken rewrite lemma, the target inequality itself is false. Using the same instantiation `b = s = void`, `n = delta void`:

* `kappa (recDelta b s (delta n)) = kappa (recDelta void void (delta (delta void))) = 1` (as computed above).
* `kappa (app s (recDelta b s n)) = max(kappa void, kappa (recDelta void void (delta void)))`.
  `kappa (recDelta void void (delta void)) = max(max(0,0), kappa void) + 1 = 1`.
  So `kappa (app s (recDelta b s n)) = max(0,1) = 1`.

The required strict inequality `1 < 1` is false. So `kappa_rec_succ_drop` is not just blocked by a bad lemma choice — it is a false statement, confirmed directly.

### Root cause

`kappa` treats "the third argument of `recDelta` is `delta`-headed" as a binary flag contributing `+1`, rather than counting how many `delta` layers are stacked there. Consequently, once `n` has **two or more** nested `delta`s, peeling off one layer via `R_rec_succ` leaves `n` still `delta`-headed, so `kappa` stays exactly the same (plateaus at the same value) instead of strictly decreasing. This is exactly the scenario needed for termination of the `R_rec_succ` rule on deeply nested `delta` chains, and it is precisely where the measure fails.

### Conclusion

The two lemmas as stated are **not sound**: `kappa_rec_delta_step` is false whenever `n` is itself `delta`-headed, and `kappa_rec_succ_drop` is false on the same instances (witnessed concretely by `b = s = void`, `n = delta void`, where both sides of the claimed strict inequality equal `1`). The `kappa` measure as defined does not strictly decrease under `R_rec_succ` in general, so this termination strategy cannot be completed as written; `kappa`'s treatment of nested `delta` chains inside `recDelta`'s third argument needs to be revised (e.g., to count the actual nesting depth) before these two theorems could become true and provable.
