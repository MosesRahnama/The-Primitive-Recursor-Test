No. The helper strategy is not sound as written.

The issue is the claimed theorem

- `kappa_rec_delta_step (b s n : Trace) :
  kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1`

This is false in general.

## Why it fails

By definition:

- `kappa (recDelta b s (delta n)) = max (max (kappa b) (kappa s)) (kappa n) + 1`

For `kappa (recDelta b s n)`, there are two cases:

1. If `n` is syntactically of the form `delta m`, then
   - `kappa (recDelta b s n)` is also computed by the special clause and may itself have a `+ 1`.

2. Otherwise,
   - `kappa (recDelta b s n) = max (max (kappa b) (kappa s)) (kappa n)`.

So the claimed equality only holds in case 2. It fails in case 1.

## Concrete counterexample

Take

- `b = void`
- `s = void`
- `n = delta void`

Then:

- `kappa b = 0`
- `kappa s = 0`
- `kappa n = kappa (delta void) = 0`

Compute the left side:

- `kappa (recDelta void void (delta (delta void)))`
- since the third argument is `delta (...)`, the special clause applies:
- `= max (max 0 0) 0 + 1`
- `= 1`

Compute the right side:

- `kappa (recDelta void void (delta void)) + 1`
- again special clause:
- `kappa (recDelta void void (delta void)) = max (max 0 0) 0 + 1 = 1`
- so right side `= 1 + 1 = 2`

Thus the theorem claims `1 = 2`, impossible.

So `kappa_rec_delta_step` is false.

---

## What about the second theorem?

The second theorem is

- `kappa_rec_succ_drop (b s n : Trace) :
  kappa (app s (recDelta b s n)) < kappa (recDelta b s (delta n))`

Using definitions:

- `kappa (app s (recDelta b s n)) = max (kappa s) (kappa (recDelta b s n))`
- `kappa (recDelta b s (delta n)) = max (max (kappa b) (kappa s)) (kappa n) + 1`

This theorem is also false in general.

### Counterexample

Again let

- `b = void`
- `s = void`
- `n = delta void`

Then:

- right side:
  - `kappa (recDelta void void (delta (delta void))) = 1`

- left side:
  - `kappa (app void (recDelta void void (delta void)))`
  - `= max (kappa void) (kappa (recDelta void void (delta void)))`
  - `= max 0 1`
  - `= 1`

So the theorem would require `1 < 1`, false.

Hence the second helper theorem also fails.

---

## Structural reason for failure

The measure `kappa` treats `delta` as measure-preserving:

- `kappa (delta t) = kappa t`

But for `recDelta`, the measure gets an extra `+1` whenever the third argument is syntactically `delta n`.

This means the value of `kappa (recDelta b s n)` depends not just on `kappa n`, but on whether `n` is syntactically a `delta`-term. Therefore you cannot generally relate

- `kappa (recDelta b s (delta n))`

to

- `kappa (recDelta b s n)`

by a uniform `+1`, because `n` itself may already be a `delta`-term and trigger the special clause on the right.

---

## Implication for the intended termination argument

For the rewrite rule

- `recDelta b s (delta n) -> app s (recDelta b s n)`

the proposed helpers seem intended to show strict decrease of `kappa`. But `kappa` does not strictly decrease for this rule in general.

Indeed, with `n = delta void`, both sides have measure `1`:

- source: `kappa (recDelta void void (delta (delta void))) = 1`
- target: `kappa (app void (recDelta void void (delta void))) = 1`

So `kappa` is not a valid strictly decreasing measure for all `Step`s.

## Conclusion

The helper strategy is unsound as written:

- `kappa_rec_delta_step` is false.
- `kappa_rec_succ_drop` is false.
- Therefore `kappa` does not provide the intended strict descent argument for `R_rec_succ` in full generality.
