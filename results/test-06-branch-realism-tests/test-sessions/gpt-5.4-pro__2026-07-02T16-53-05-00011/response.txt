No. The helper strategy is not sound as written.

## Main issue: `kappa_rec_delta_step` is false

Write

- `B := kappa b`
- `S := kappa s`
- `N := kappa n`
- `M := Nat.max (Nat.max B S) N`

Then by definition,

\[
\kappa(\mathrm{recDelta}\ b\ s\ (\delta n)) = M + 1.
\]

But the right-hand side of the proposed theorem depends on the **syntactic shape** of `n`:

### Case 1: `n` is **not** of the form `delta _`
Then

\[
\kappa(\mathrm{recDelta}\ b\ s\ n)=M,
\]

so indeed

\[
\kappa(\mathrm{recDelta}\ b\ s\ (\delta n)) = \kappa(\mathrm{recDelta}\ b\ s\ n)+1.
\]

### Case 2: `n = delta m`
Then the special `recDelta ... (.delta _)` clause applies on the RHS too, so

\[
\kappa(\mathrm{recDelta}\ b\ s\ n)
= \kappa(\mathrm{recDelta}\ b\ s\ (\delta m))
= \max(\max B S,\kappa m)+1.
\]

Also `\kappa n = \kappa(\delta m)=\kappa m`, so the left-hand side is

\[
\kappa(\mathrm{recDelta}\ b\ s\ (\delta n))
= \kappa(\mathrm{recDelta}\ b\ s\ (\delta(\delta m)))
= \max(\max B S,\kappa m)+1.
\]

Thus in this case

\[
\kappa(\mathrm{recDelta}\ b\ s\ (\delta n))
= \kappa(\mathrm{recDelta}\ b\ s\ n),
\]

not `... = ... + 1`.

### Concrete counterexample
Take `b = void`, `s = void`, `n = delta void`.

Then:

- `kappa (recDelta void void (delta (delta void))) = 1`
- `kappa (recDelta void void (delta void)) = 1`

So the theorem claims

\[
1 = 1 + 1,
\]

which is false.

---

## Therefore `kappa_rec_succ_drop` is also false

Using the same counterexample:

- `kappa (recDelta void void (delta (delta void))) = 1`
- `kappa (app void (recDelta void void (delta void))) = max 0 1 = 1`

So the theorem claims

\[
1 < 1,
\]

which is false.

More generally:

- If `n` is not `delta _`, then the strict drop does hold.
- If `n = delta m`, then both sides have the same `kappa`.

So the best unconditional statement here is `≤`, not `<`.

---

## Why this happens

`kappa` ignores `delta` almost everywhere:

- `kappa (delta t) = kappa t`

but gives `recDelta b s (delta n)` a one-time bonus `+1`.

So if the third argument already starts with `delta`, stripping one `delta` in the `R_rec_succ` step does **not** necessarily reduce `kappa`; the bonus remains present on `recDelta b s n`.

In fact, for any term with at least one leading `delta`, `kappa (recDelta b s ...)` only remembers “has a leading delta”, not “how many”.

---

## Broader termination concern

Even aside from these two lemmas, `kappa` is not a strict descent measure for several rewrite rules:

- `merge void t → t` gives  
  `kappa (merge void t) = max 0 (kappa t) = kappa t`
- `merge t void → t` same
- `merge t t → t` same
- `eqW a b → integrate (merge a b)` gives  
  `kappa (eqW a b) = max (kappa a) (kappa b) = kappa (integrate (merge a b))`
- `integrate (delta t) → void` is only strict when `kappa t > 0`

So `kappa` by itself cannot support a global “every step strictly decreases” termination proof.

---

## Conclusion

The helper strategy is **unsound as written**:

1. `kappa_rec_delta_step` is false in general.
2. `kappa_rec_succ_drop` is also false in general.
3. More broadly, `kappa` is not a strict decreasing measure for the full rewrite system.

A termination argument would need either:

- a corrected, more refined measure, or
- extra side conditions (for example, excluding the case `n = delta _`), or
- a lexicographic/multicomponent measure rather than `kappa` alone.
