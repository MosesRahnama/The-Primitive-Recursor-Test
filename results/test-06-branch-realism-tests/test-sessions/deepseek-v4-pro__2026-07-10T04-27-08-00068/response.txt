The helper strategy is **unsound**.

**Reasoning**

The problematic theorem is  
```lean
theorem kappa_rec_delta_step (b s n : Trace) :
  kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1 := by
  sorry
```

In the definition of `kappa`, the clauses for `recDelta` are overlapping patterns:

```
| .recDelta b s (.delta n) => Nat.max (Nat.max (kappa b) (kappa s)) (kappa n) + 1
| .recDelta b s n          => Nat.max (Nat.max (kappa b) (kappa s)) (kappa n)
```

The first equation applies when the third argument is a `delta`, the second is a catch‑all.  
For an arbitrary `n : Trace`, we have  
`kappa (recDelta b s (delta n)) = max(max(kappa b, kappa s), kappa n) + 1`.  
However, `kappa (recDelta b s n)` is only **definitionally/propositionally** equal to `max(max(kappa b, kappa s), kappa n)` when `n` does **not** start with `delta`. If `n` itself is a `delta` term, the first clause applies and the equality fails.

**Counterexample**

Take `b = void`, `s = void`, `n = delta void`.  
`kappa void = 0`.

- LHS: `kappa (recDelta void void (delta (delta void)))`  
  = `max(max(0, 0), kappa (delta void)) + 1`  
  = `max(0, kappa void) + 1`  
  = `0 + 1 = 1`.

- RHS: `kappa (recDelta void void n) + 1`  
  = `kappa (recDelta void void (delta void)) + 1`  
  = `(max(max(0, 0), kappa void) + 1) + 1`  
  = `1 + 1 = 2`.

`1 ≠ 2`, so `kappa_rec_delta_step` is false in general.

Because the subsequent lemma `kappa_rec_succ_drop` relies on this false equality, any termination argument built on these two helpers is unsound.
