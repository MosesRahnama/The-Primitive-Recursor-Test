# Assessment: The helper strategy is **UNSOUND**

Both helper theorems are false as stated. Let me demonstrate with calculations.

## Analyzing `kappa_rec_delta_step`

The claim is:
```
kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1
```

**Left side** (via `kappa_rec_delta`):
```
kappa (recDelta b s (delta n)) = max (max (kappa b) (kappa s)) (kappa n) + 1
```

**Right side** — here's the problem. The value of `kappa (recDelta b s n)` depends on the *shape* of `n`, because of the overlapping pattern match in `kappa`:

- **Case `n = delta m`**: the first `recDelta` pattern fires:
  ```
  kappa (recDelta b s (delta m)) = max (max (kappa b) (kappa s)) (kappa m) + 1
  ```
- **Case `n` not a `delta`**: the fallback pattern fires:
  ```
  kappa (recDelta b s n) = max (max (kappa b) (kappa s)) (kappa n)
  ```

### Counterexample to `kappa_rec_delta_step`

Take `n = delta void`, `b = void`, `s = void`.

**LHS:** `kappa (recDelta void void (delta (delta void)))`
```
= max (max 0 0) (kappa (delta void)) + 1 = max 0 0 + 1 = 0 + 1 = 1
```
(since `kappa (delta void) = kappa void = 0`)

**RHS:** `kappa (recDelta void void (delta void)) + 1`
```
= (max (max 0 0) (kappa void) + 1) + 1 = 1 + 1 = 2
```

So `1 = 2` is required — **false**. The theorem cannot be proved.

The intended equation only holds when `n` is *not* of the form `delta _`. When `n = delta m`, both sides carry a `+1` from the `recDelta`‑over‑`delta` clause, and the equation fails by an off-by-one.

## Analyzing `kappa_rec_succ_drop`

The claim is:
```
kappa (app s (recDelta b s n)) < kappa (recDelta b s (delta n))
```

**LHS:**
```
kappa (app s (recDelta b s n)) = max (kappa s) (kappa (recDelta b s n))
```

**RHS:**
```
max (max (kappa b) (kappa s)) (kappa n) + 1
```

### Counterexample when `n = delta m`

Let `n = delta void`, `b = void`, `s = void`.

**LHS:** `kappa (app void (recDelta void void (delta void)))`
```
= max (kappa void) (kappa (recDelta void void (delta void)))
= max 0 (max (max 0 0) (kappa void) + 1) = max 0 1 = 1
```

**RHS:** `kappa (recDelta void void (delta (delta void)))`
```
= max (max 0 0) (kappa (delta void)) + 1 = 0 + 1 = 1
```

So the claim requires `1 < 1` — **false**.

The proof stub tries `rw [kappa_rec_delta_step]`, which rewrites the RHS to `kappa (recDelta b s n) + 1`. But since `kappa_rec_delta_step` is itself false, this rewrite is unjustified. Even granting it, the resulting goal
```
max (kappa s) (kappa (recDelta b s n)) < kappa (recDelta b s n) + 1
```
still fails whenever `kappa s > kappa (recDelta b s n)`, e.g. take `s` large and `n = void`, `b = void`:
- With `s` having `kappa s = 5`, `n = void`, `b = void`: LHS `= max 5 0 = 5`, and `kappa (recDelta ... void) + 1 = 0 + 1 = 1`, so `5 < 1` is false.

## Root cause

The overlapping / non-uniform definition of `kappa` on `recDelta`:
- The `recDelta b s (delta n)` clause adds `+1`, but the general `recDelta b s n` clause does not.
- This makes `kappa (recDelta b s n)` discontinuous in the head shape of `n`, so `kappa_rec_delta_step` has no uniform truth value.
- Moreover, `kappa` **ignores `s` inside the `recDelta` measure** (only `kappa s` appears as a `max` argument), yet the reduct `app s (...)` re-exposes `kappa s` at top level, so an arbitrarily large `s` breaks the strict-decrease claim.

## Conclusion

The helper strategy is **not sound**. Both `kappa_rec_delta_step` and `kappa_rec_succ_drop` are refutable by explicit traces, so the two `sorry`s can never be discharged. A viable measure must (a) treat `recDelta` uniformly (a `+1` that does not depend on whether the third argument is a `delta`), and (b) account for `kappa s` in the `recDelta` measure so that peeling off `app s (…)` in `R_rec_succ` genuinely decreases the value.
