The helper strategy is **not sound**. Both theorems `kappa_rec_delta_step` and `kappa_rec_succ_drop` are **false** under the given definition of `kappa`, as demonstrated by explicit counterexamples. Below is the rigorous assessment.

---

### **1. Failure of `kappa_rec_delta_step`**
**Theorem claim**:  
`kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1`  
**Counterexample**:  
Let `b = void`, `s = void`, `n = delta void`.  
- **LHS**: `kappa (recDelta void void (delta (delta void)))`  
  Third argument is `delta (delta void)` → matches first `recDelta` clause in `kappa`:  
  `= Nat.max (Nat.max (kappa void) (kappa void)) (kappa (delta void)) + 1`  
  `= Nat.max (Nat.max 0 0) (kappa void) + 1` (by `kappa_delta`)  
  `= Nat.max 0 0 + 1 = 1`.  
- **RHS**: `kappa (recDelta void void (delta void)) + 1`  
  Third argument is `delta void` → matches first `recDelta` clause:  
  `kappa (recDelta void void (delta void)) = Nat.max (Nat.max 0 0) (kappa void) + 1 = 1`,  
  so RHS `= 1 + 1 = 2`.  
**Result**: `1 = 2` is **false**.  
**Root cause**: The definition of `kappa` for `recDelta b s n` depends *syntactically* on whether `n` is a `delta` constructor. When `n` itself contains `delta` (e.g., `n = delta void`), `kappa (recDelta b s n)` uses the *first clause* of `kappa`'s `recDelta` pattern (adding `+1`), breaking the claimed equality. The theorem incorrectly assumes `kappa (recDelta b s n)` always uses the "catch-all" clause.

---

### **2. Failure of `kappa_rec_succ_drop`**
**Theorem claim**:  
`kappa (app s (recDelta b s n)) < kappa (recDelta b s (delta n))`  
**Counterexample**: Same inputs: `b = void`, `s = void`, `n = delta void`.  
- **LHS**: `kappa (app void (recDelta void void (delta void)))`  
  `kappa (recDelta void void (delta void)) = 1` (as above),  
  `kappa (app void ...) = Nat.max (kappa void, 1) = Nat.max 0 1 = 1`.  
- **RHS**: `kappa (recDelta void void (delta (delta void))) = 1` (computed in §1).  
**Result**: `1 < 1` is **false** (equality holds).  
**Root cause**:  
- When `n` is a `delta` constructor, `kappa (recDelta b s n)` may already include a `+1` (via the first `recDelta` clause in `kappa`).  
- The RHS `kappa (recDelta b s (delta n))` does *not* necessarily exceed the LHS because the structural "depth" added by the outer `delta` in `(delta n)` is offset by the inner structure of `n`.  
- The rewrite rule `R_rec_succ` produces a term (`app s (recDelta b s n)`) whose `kappa` value can equal the original term's `kappa`, violating strict decrease.

---

### **3. Critical Flaw in Termination Strategy**
The rewrite step `R_rec_succ`:  
`recDelta b s (delta n) ↦ app s (recDelta b s n)`  
**does not strictly decrease `kappa`** in the counterexample:  
`kappa (recDelta void void (delta (delta void))) = 1`  
`kappa (app void (recDelta void void (delta void))) = 1`.  
Since `kappa` is non-decreasing here, it **cannot** serve as a termination measure for this rule. The helper theorems attempt to force a decrease via unsound algebraic manipulations, but the counterexample proves the measure itself is inadequate for `R_rec_succ`.

---

### **Conclusion**
- `kappa_rec_delta_step` is **mathematically false** (counterexample invalidates equality).  
- `kappa_rec_succ_drop` is **mathematically false** (counterexample shows non-strict inequality).  
- The core issue is that `kappa`'s definition for `recDelta` is **syntactically sensitive** to the *exact constructor* of its third argument. When nested `delta` constructors exist, the measure fails to reflect the structural reduction intended by `R_rec_succ`.  
- **No modification of proofs** (e.g., filling `sorry`) can salvage these theorems—they are inherently contradicted by the semantics of `kappa`. A sound termination argument would require a revised measure (e.g., one tracking nested `delta` depth explicitly) or a lexicographic combination of measures.  

The helper strategy is **unsound** and **cannot support termination** for the given rewrite system.
