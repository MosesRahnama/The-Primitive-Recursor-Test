No — the helper strategy is not sound as written.

### Core issue

`kappa` treats `delta` as measure-neutral:

- `kappa (delta t) = kappa t`

But for `recDelta`, it gives a **one-time bonus** when the third argument is *syntactically* `delta _`:

- `kappa (recDelta b s (delta n)) = max (max (kappa b) (kappa s)) (kappa n) + 1`
- `kappa (recDelta b s n) = max (max (kappa b) (kappa s)) (kappa n)` only when `n` is **not** syntactically `delta _`

So adding one more `delta` does **not** always add 1 to `kappa`.

---

## 1. `kappa_rec_delta_step` is false in general

The theorem claims:

```lean
kappa (recDelta b s (delta n)) = kappa (recDelta b s n) + 1
```

Let

- `M := Nat.max (Nat.max (kappa b) (kappa s)) (kappa n)`.

Then always:

- `kappa (recDelta b s (delta n)) = M + 1`.

But `kappa (recDelta b s n)` depends on the **shape** of `n`:

- if `n` is not `delta _`, then `kappa (recDelta b s n) = M`
- if `n = delta m`, then `kappa (recDelta b s n) = M + 1`

So in the nested-`delta` case, the theorem would assert:

- `M + 1 = (M + 1) + 1`

which is impossible.

### Concrete counterexample

Take:

- `b = void`
- `s = void`
- `n = delta void`

Then:

- `kappa void = 0`
- `kappa (delta void) = 0`

So:

- `kappa (recDelta void void (delta (delta void))) = 0 + 1 = 1`
- `kappa (recDelta void void (delta void)) = 0 + 1 = 1`

Hence the theorem claims:

- `1 = 1 + 1`
- i.e. `1 = 2`

False.

---

## 2. `kappa_rec_succ_drop` is also false in general

The theorem claims:

```lean
kappa (app s (recDelta b s n)) < kappa (recDelta b s (delta n))
```

Again let `n = delta m`, and let

- `M := Nat.max (Nat.max (kappa b) (kappa s)) (kappa m)`.

Then:

- `kappa (recDelta b s n) = M + 1`
- `kappa (recDelta b s (delta n)) = M + 1`

Also:

- `kappa (app s (recDelta b s n)) = Nat.max (kappa s) (M + 1) = M + 1`

because `M ≥ kappa s`.

So in this case:

- `kappa (app s (recDelta b s n)) = kappa (recDelta b s (delta n))`

not a strict inequality.

### Concrete counterexample

Same choice:

- `b = void`
- `s = void`
- `n = delta void`

Then:

- `kappa (app void (recDelta void void (delta void))) = max 0 1 = 1`
- `kappa (recDelta void void (delta (delta void))) = 1`

So the theorem claims:

- `1 < 1`

False.

---

## 3. What the measure is actually tracking

For `recDelta`, `kappa` distinguishes only:

- third argument is **not** `delta _`  → no bonus
- third argument **is** `delta _`      → `+1`

It does **not** count how many leading `delta`s there are.

In fact, with `b = s = void`:

- `kappa (recDelta void void void) = 0`
- `kappa (recDelta void void (delta void)) = 1`
- `kappa (recDelta void void (delta (delta void))) = 1`
- `kappa (recDelta void void (delta (delta (delta void)))) = 1`

So once the third argument is already `delta`-headed, adding another `delta` does not increase the measure.

That is exactly why the helper lemmas fail.

---

## 4. Broader termination note

Even beyond these two lemmas, `kappa` is not a strict descent measure for all `Step` rules:

- `merge void t -> t` preserves `kappa`
- `merge t void -> t` preserves `kappa`
- `merge t t -> t` preserves `kappa`
- `eqW a b -> integrate (merge a b)` preserves `kappa`
- `recDelta b s (delta n) -> app s (recDelta b s n)` can preserve `kappa` in the nested-`delta` case above

So a global termination proof cannot rely on “every step strictly decreases `kappa`” with this definition.

---

## Conclusion

The helper strategy is **unsound as written**.

- `kappa_rec_delta_step` is false.
- `kappa_rec_succ_drop` is also false.
- The failure happens whenever `n` is already of the form `delta m`.

So if these `sorry`s were replaced by actual proofs in a sound development, they would not go through from the given definitions.
